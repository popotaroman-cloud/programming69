## Lab: แปลง Pseudocode → Python (ไฟล์ใหม่ — อัปเดตโครงสร้างเป็น 3 ระดับ x 4 ข้อ = 12 ข้อ)
ไฟล์ใหม่ `week_06_function/lab_pseudocode_to_python.md` — **ปรับโครงสร้างจากเดิม 10 ข้อเรียงยาก-ง่ายรวด เป็นแบ่งตาม 3 ระดับ (พื้นฐาน/กลาง/สูง) ระดับละ 4 ข้อ** โดยทั้ง 4 ข้อในแต่ละระดับมี**ระดับการให้ scaffolding ต่างกัน** (ไล่จากมี scaffold เต็มไปจนไม่มีเลย) ไม่ใช่ไล่ตามความยากของหัวข้ออีกต่อไป:

| ข้อที่ในแต่ละระดับ | รูปแบบ | คำอธิบาย |
|---|---|---|
| ข้อ 1 | **Pseudocode** | ให้ pseudocode มาตรฐาน (`FUNCTION`, `IF`, `RETURN`, `FOR EACH` ฯลฯ) ให้แปลงเป็น Python ตรง ๆ (รูปแบบเดิมที่ใช้อยู่แล้ว) |
| ข้อ 2 | **คำอธิบายขั้นตอน (เป็นข้อความ)** | อธิบายอัลกอริทึมเป็นร้อยแก้ว/ลำดับขั้นตอนภาษาธรรมชาติ (ไม่ใช่ pseudocode เชิงโครงสร้าง) ให้ผู้เรียนแปลงเป็น Python เอง — ฝึกอ่านจับ logic จากคำบรรยาย ไม่ใช่แค่แปลง syntax |
| ข้อ 3 | **คำอธิบายขั้นตอน (เป็นข้อความ)** | เหมือนข้อ 2 แต่โจทย์คนละสถานการณ์ ความยากใกล้เคียงกัน |
| ข้อ 4 | **บอกแค่โจทย์/requirement (pain point)** | ให้แค่สถานการณ์ปัญหา/ความต้องการ (เช่น "ร้านค้าต้องการคำนวณส่วนลดตามเงื่อนไข...") ไม่มี pseudocode หรือขั้นตอนกำกับเลย ผู้เรียนต้องคิดเองทั้งหมดตั้งแต่ออกแบบฟังก์ชันจนถึงเขียนโค้ด — ยากสุดในระดับนั้น |

รวมทั้งไฟล์: 3 ระดับ x 4 ข้อ = **12 ข้อ** โดยแต่ละระดับใช้แนวคิดของระดับนั้นเป็นหลัก (พื้นฐาน = หัวข้อ 1–5, กลาง = หัวข้อ 6–9, สูง = หัวข้อ 10–15) และทั้ง 12 ข้อยังต้องคาบเกี่ยวแนวคิดหลากหลายภายในระดับตัวเอง (ไม่ใช้แนวคิดเดียวซ้ำทั้ง 4 ข้อ)

โครงสร้างไฟล์: แบ่งเป็น 3 section ตามระดับ (`## ระดับพื้นฐาน`, `## ระดับกลาง`, `## ระดับสูง`) แต่ละ section มี 4 ข้อย่อยตามตารางด้านบน จากนั้นจึงเป็นหมวด "## เฉลย" รวมท้ายไฟล์ (แยกตามระดับเช่นเดียวกัน ไม่ปนกับตัวโจทย์)

รูปแบบต่อ 1 ข้อ (ปรับตามประเภทข้อ):
- **ข้อ 1 (pseudocode)**: โจทย์ (สถานการณ์สั้น ๆ) → Pseudocode → คำสั่งให้แปลงเป็น Python
- **ข้อ 2–3 (คำอธิบายขั้นตอน)**: โจทย์ (สถานการณ์สั้น ๆ) → คำอธิบายขั้นตอนเป็นร้อยแก้ว (ไม่มี pseudocode) → คำสั่งให้เขียน Python จากคำอธิบายนั้น
- **ข้อ 4 (โจทย์/pain point ล้วน)**: โจทย์/requirement เท่านั้น (ไม่มี pseudocode ไม่มีขั้นตอน) → คำสั่งให้ออกแบบและเขียนฟังก์ชันเอง
- **เฉลย (ทุกข้อ)**: โค้ด Python จริง มีเลขบรรทัดกำกับ + รันจริงยืนยัน Output ตามกฎ Verification เดียวกับไฟล์อื่น (เก็บไว้ในหมวด "เฉลย" แยกท้ายไฟล์เช่นเดียวกับ practice)

ไม่ต้องมี trace table/คำอธิบายภาพรวมแบบเต็มเหมือนตัวอย่างในเนื้อหาบท (lab เน้นให้ฝึกเขียนเอง ไม่ใช่บทเรียน) แต่เฉลยต้องมี Output ที่รันจริงกำกับเสมอ

## องค์ประกอบของ "1 ตัวอย่าง" (นิยามใหม่ — เข้มขึ้น)
ทุกตัวอย่างที่นับใน "กฎขั้นต่ำ" ด้านบน ต้องมีครบ 4 ส่วนนี้เสมอ ขาดส่วนใดส่วนหนึ่งถือว่าไม่นับเป็นตัวอย่างที่สมบูรณ์:

1. **โค้ดพร้อมเลขบรรทัดกำกับ** — ทุก code block ใส่เลขบรรทัดชิดซ้ายของแต่ละบรรทัด (รูปแบบ 2 หลัก เช่น `01  def add(x, y):`) เพื่อให้ trace table และคำอธิบายอ้างอิงเลขบรรทัดได้ตรงกัน
2. **Output ที่ผ่านการรันจริง** — ห้ามเดา ต้องรันโค้ดจริงก่อนคัดลอกผลลัพธ์มาใส่ (ดูหัวข้อ "การทดสอบตัวอย่างโค้ด" ด้านล่าง)
3. **ตารางการเปลี่ยนแปลงค่า (trace table)** — ตารางแสดงลำดับการทำงานทีละขั้น คอลัมน์มาตรฐาน: `บรรทัดที่ | คำสั่งที่ทำงาน | ตัวแปร/ค่า ณ จุดนั้น | หมายเหตุ`
4. **คำอธิบายภาพรวม** — ย่อหน้าอธิบายโค้ดทั้งบล็อกในเชิงภาพรวม (อ้างอิงช่วงบรรทัด เช่น "บรรทัด 1–3 ทำหน้าที่...") ไม่ใช่ไล่อธิบายทีละบรรทัดซ้ำกับ trace table แต่สรุปว่าโค้ดส่วนนั้นทำอะไรและทำไม

**ตัวอย่างรูปแบบมาตรฐาน:**

````
```python
01  def add(x, y):
02      result = x + y
03      return result
04
05  print(add(3, 5))
```

**Output:**
```
8
```

**ตารางการเปลี่ยนแปลงค่า:**

| บรรทัดที่ | คำสั่งที่ทำงาน | ตัวแปร/ค่า | หมายเหตุ |
|---|---|---|---|
| 5 | เรียก `add(3, 5)` | x=3, y=5 | เข้าสู่ scope ของฟังก์ชัน add |
| 2 | `result = x + y` | result=8 | คำนวณผลรวมในตัวแปร local |
| 3 | `return result` | คืนค่า 8 | ออกจากฟังก์ชัน กลับไปที่บรรทัด 5 |
| 5 | `print(...)` | แสดงผล 8 | พิมพ์ค่าที่ได้รับคืนออกทางหน้าจอ |

**คำอธิบายภาพรวม:** บรรทัด 1–3 นิยามฟังก์ชัน `add` ที่รับพารามิเตอร์ `x` และ `y` แล้วคืนค่าผลรวม บรรทัด 5 เรียกใช้ฟังก์ชันด้วยอาร์กิวเมนต์ 3 และ 5 ทำให้ได้ผลลัพธ์ 8 ซึ่งถูกส่งต่อให้ `print` แสดงผลทันที
````

## การทดสอบตัวอย่างโค้ด (Verification) — บังคับทุกตัวอย่าง
- ก่อนใส่โค้ดตัวอย่างลงในเอกสาร ต้องรันจริงด้วย Python interpreter ผ่าน Bash/PowerShell tool ในเครื่องก่อนเสมอ
- ขั้นตอน: เขียนไฟล์ `.py` ชั่วคราวใน scratchpad → รันด้วย `python` → คัดลอก stdout จริงมาใส่เป็น **Output** → บันทึกเลข exit code ถ้ามี error ต้องแก้โค้ดตัวอย่างจนรันผ่านจริง
- ห้ามคัดลอก output จากเว็บต้นทาง (W3Schools/TutorialsPoint/GeeksforGeeks) มาใส่ตรง ๆ โดยไม่รันซ้ำ เพราะบางเว็บมีตัวอย่างที่พิมพ์ผิดหรือใช้ syntax เวอร์ชันเก่า
- ไฟล์ .py ทดสอบเก็บไว้ใน scratchpad ระหว่างทำงาน ไม่ต้อง commit เข้า repo

## มาตรฐานภาษาและศัพท์เทคนิค (Style Guide)
- ใช้ภาษาไทยทางการ (เลี่ยงภาษาพูด คำย่อไม่เป็นทางการ เช่น "เดี๋ยว", "โอเค", "ก็คือ") น้ำเสียงแบบเอกสารประกอบการสอนระดับอุดมศึกษา
- ศัพท์เทคนิคภาษาอังกฤษที่ไม่มีคำไทยที่ใช้แพร่หลายให้คงรูปเดิม (ไม่บัญญัติศัพท์เอง) และใช้คำเดียวกันตลอดทั้ง 3 ไฟล์ — ยึดตาม**ตารางศัพท์มาตรฐาน**นี้:

| English | ใช้คำว่า |
|---|---|
| function | ฟังก์ชัน |
| parameter | พารามิเตอร์ |
| argument | อาร์กิวเมนต์ |
| return value | ค่าที่ส่งกลับ |
| scope | ขอบเขต (ตัวแปร) |
| local variable | ตัวแปรเฉพาะที่ (local) |
| global variable | ตัวแปรส่วนกลาง (global) |
| recursion | การเรียกซ้ำ (recursion) |
| base case | กรณีฐาน (base case) |
| default argument | อาร์กิวเมนต์ค่าเริ่มต้น |
| positional argument | อาร์กิวเมนต์ตามตำแหน่ง |
| keyword argument | อาร์กิวเมนต์แบบระบุชื่อ |
| arbitrary arguments (*args/**kwargs) | อาร์กิวเมนต์จำนวนไม่จำกัด |
| lambda | ฟังก์ชันนิรนาม (lambda) |
| higher-order function | ฟังก์ชันอันดับสูง (higher-order function) |
| pure function | ฟังก์ชันบริสุทธิ์ (pure function) |
| side effect | ผลข้างเคียง (side effect) |
| first-class function | ฟังก์ชันชั้นหนึ่ง (first-class function) |
| closure | Closure (คงศัพท์เดิม) |

- ก่อนปิดงานทั้ง 3 ไฟล์ (Step 7) จะไล่ตรวจอีกรอบว่าไม่มีคำแปลไทยที่สะกดต่างกันในแต่ละไฟล์ (เช่น ไฟล์หนึ่งใช้ "ตัวแปรเฉพาะที่" อีกไฟล์ใช้ "ตัวแปรท้องถิ่น" ต้องเลือกใช้แบบเดียว)

## Audit Checklist ต่อหัวข้อ (ใช้ตรวจก่อนปิดงานแต่ละหัวข้อ)
ก่อนถือว่าหัวข้อใดหัวข้อหนึ่ง "เสร็จ" ต้องผ่านทุกข้อนี้:

- [ ] **Source coverage**: ระบุแหล่งอ้างอิง (W3/TP/GfG) ที่ใช้จริงไว้ท้ายหัวข้อ หรือระบุ "เสริมเอง ไม่อ้างอิงจากสามแหล่งนี้" ถ้าไม่มีแหล่งตรง
- [ ] **Example count**: จำนวนตัวอย่างโค้ดถึงขั้นต่ำ **3 ตัวอย่างทุกระดับ** (ตามตารางด้านบน) แต่ละตัวอย่างครบ 4 องค์ประกอบ (โค้ดมีเลขบรรทัด + output ที่รันจริง + trace table + คำอธิบายภาพรวม) และทั้ง 3 ตัวอย่างต้องคนละโดเมนปัญหากัน (ดูเกณฑ์ "หลากหลาย")
- [ ] **Practice/Lab coverage**: ไฟล์นั้นมีหมวดแบบฝึกหัดท้ายบท ≥20 ข้อ (มีเฉลยรันจริงแยกหมวด) — และถ้าเป็นรอบสร้าง lab ให้ตรวจว่า `lab_pseudocode_to_python.md` มีครบ 3 ระดับ x 4 ข้อ = 12 ข้อ ตามสัดส่วน (1 pseudocode / 2 คำอธิบายขั้นตอน / 1 โจทย์ล้วน ต่อระดับ)
- [ ] **Verified output**: ยืนยันว่ารันโค้ดจริงแล้วก่อนใส่ output ลงเอกสาร (ไม่ใช่คัดลอกจากเว็บต้นทาง)
- [ ] **Formal language**: ตรวจว่าใช้ภาษาไทยทางการ และศัพท์เทคนิคตรงกับตารางศัพท์มาตรฐาน
- [ ] **Language-agnostic framing**: ย่อหน้าอธิบายแนวคิดต้องพูดถึงแนวคิดก่อนพูดถึง syntax Python (ไม่ใช่บอก syntax แล้วค่อยสรุปแนวคิด)
- [ ] **Scope note**: มีหมายเหตุชัดเจนว่าอยู่ในขอบเขตสอบของ `slides/06_function.md` หรือเป็นเนื้อหาเสริม
- [ ] **Cross-link**: ถ้าเชื่อมกับหัวข้ออื่นในเอกสาร (เช่น 8 ต่อจาก 3) มีลิงก์อ้างอิงในเนื้อหา
- [ ] **Conflict check**: ตัวอย่างไม่ขัดกับกฎของสไลด์เดิม (เช่น "return ค่าเดียวเสมอ") ถ้าขัด ต้องมีหมายเหตุเตือนกำกับ

จะรวบผลตรวจ (checklist ผ่าน/ไม่ผ่านของทั้ง 15 หัวข้อ) ไว้เป็นตารางสรุปท้าย plan.md หลังเขียนเสร็จ เพื่อให้ตรวจทานง่ายในครั้งเดียว

## ขั้นตอนการสร้างเนื้อหา "ต่อ 1 หัวข้อ" (ทำซ้ำ 15 รอบ — อัปเดตเป็น 9 ขั้นย่อย)
สำหรับหัวข้อแต่ละข้อ (1–15) จะทำตามลำดับนี้:

1. **Fetch แหล่งอ้างอิง** — ใช้ WebFetch ดึงเนื้อหาหน้าเฉพาะที่ map ไว้ (W3Schools / TutorialsPoint / GeeksforGeeks ตามตาราง mapping) เพื่อดึงคำอธิบาย + ตัวอย่างต้นฉบับที่เว็บใช้สอน
   - หัวข้อที่ไม่มีหน้าตรง (13, 15) จะข้ามขั้นนี้ และใช้ความรู้ทั่วไปด้าน software engineering แทน โดยจะระบุในเอกสารว่า "เสริมโดยไม่ได้อ้างอิงจากสามแหล่งนี้โดยตรง"
2. **สรุปแนวคิดแบบ language-agnostic** — เขียนคำอธิบาย 1–2 ย่อหน้าด้วยภาษาไทยทางการ ตามตารางศัพท์มาตรฐาน โดยพูดถึงแนวคิดก่อนพูดถึง syntax เฉพาะของ Python
3. **ร่างตัวอย่างโค้ด Python** — ร่างตัวอย่างตามจำนวนขั้นต่ำของระดับนั้น (2 หรือ 3 ตัวอย่าง) ใส่เลขบรรทัดกำกับทุกบรรทัด
4. **รันโค้ดจริงเพื่อยืนยัน Output** — บันทึกเป็นไฟล์ `.py` ใน scratchpad แล้วรันด้วย Bash/PowerShell จริง คัดลอก stdout จริงมาใส่เป็น **Output** (ห้ามเดาหรือคัดลอกจากเว็บต้นทางโดยไม่รันซ้ำ) ถ้า error ต้องแก้จนรันผ่าน
5. **สร้างตารางการเปลี่ยนแปลงค่า (trace table)** — ไล่ตามลำดับการทำงานจริงของโค้ด (อ้างอิงผลจาก Step 4) ใส่คอลัมน์ บรรทัดที่ / คำสั่งที่ทำงาน / ตัวแปร-ค่า / หมายเหตุ
6. **เขียนคำอธิบายภาพรวม** — สรุปโค้ดทั้งบล็อกเป็นย่อหน้า อ้างอิงช่วงบรรทัด ไม่ไล่ทีละบรรทัดซ้ำกับ trace table
7. **เชื่อมโยงกับหัวข้ออื่นในเอกสาร** — ถ้าหัวข้อนี้ต่อยอดจากหัวข้อก่อนหน้า (เช่น หัวข้อ 8 args/kwargs ต่อยอดจากหัวข้อ 3 parameter/argument) ใส่ลิงก์อ้างอิงในเนื้อหา
8. **ใส่หมายเหตุขอบเขตคอร์ส** — ระบุชัดว่าหัวข้อนี้ตรงกับที่สอนจริงใน `slides/06_function.md` (หัวข้อ 1–5, บางส่วนของ 9) หรือเป็นเนื้อหาเสริมนอกขอบเขตสอบ (หัวข้อ 6–15 ส่วนใหญ่)
9. **ตรวจสอบความขัดแย้ง + รัน audit checklist** — เช็คว่าตัวอย่างโค้ดไม่ขัดกับกฎของสไลด์เดิม (เช่น slide เดิมห้าม return หลายค่า) ถ้าขัด ใส่หมายเหตุเตือนไว้ชัดเจนแทนการลบทิ้ง แล้วไล่ audit checklist ทั้ง 8 ข้อของหัวข้อนั้นให้ผ่านครบก่อนนับว่าเสร็จ

# ระดับพื้นฐาน (หัวข้อ 1–5)

## หัวข้อ 1: จุดประสงค์ของฟังก์ชัน (DRY, Decomposition) (ระดับ: พื้นฐาน)

**Subtopic / ประเด็นย่อยที่ควรพูดถึง:**
- นิยามฟังก์ชัน: กลุ่มคำสั่งที่ถูกตั้งชื่อไว้ เรียกใช้ซ้ำได้หลายครั้งโดยไม่ต้องเขียนคำสั่งชุดเดิมซ้ำใหม่ทุกครั้ง
- หลักการ DRY (Don't Repeat Yourself): เขียนตรรกะการทำงานหนึ่งอย่างไว้เพียงจุดเดียวในโปรแกรม แล้วเรียกใช้ซ้ำเมื่อจำเป็น แทนการคัดลอกวางซ้ำหลายจุด
- เหตุผลของ DRY: หากต้องแก้ไขตรรกะในภายหลัง การมีอยู่จุดเดียวทำให้แก้ไขง่ายและลดโอกาสเกิดข้อผิดพลาด
- Decomposition: การแตกปัญหาใหญ่ที่ซับซ้อนให้กลายเป็นปัญหาย่อยหลายส่วน แต่ละส่วนเขียนเป็นฟังก์ชันของตนเอง
- ผลของ decomposition: โปรแกรมอ่านง่ายขึ้น ทดสอบแยกส่วนได้ ดูแลรักษาง่ายขึ้นในระยะยาว
- ไวยากรณ์ Python: ฟังก์ชันสร้างด้วย `def` ตามด้วยชื่อฟังก์ชันและวงเล็บ
- เมื่อมีฟังก์ชันแล้ว การนำตรรกะเดิมไปใช้ซ้ำทำได้เพียงเรียกชื่อฟังก์ชัน ไม่ต้องเขียนสูตรคำนวณซ้ำใหม่ทุกครั้ง

**ตัวอย่างที่ควรใช้ในสไลด์:**
1. คำนวณพื้นที่สี่เหลี่ยม (`calculate_area`) — โดเมน: เรขาคณิต/ตัวเลข | สาธิตอะไร: ฟังก์ชันเดียวถูกเรียกซ้ำ 3 ครั้งด้วยอาร์กิวเมนต์ต่างกัน แสดง DRY ชัดเจนที่สุด (ตรงกับ Slide 4 ของสไลด์เดิม) | โค้ดหลัก: `def calculate_area(width, height): return width * height` แล้วเรียก `calculate_area(4,5)`, `(6,2)`, `(3,3)`
2. จัดรูปแบบรายการใบเสร็จ (`format_receipt_line`) — โดเมน: ข้อความ (ไม่ใช่ตัวเลข) | สาธิตอะไร: DRY ใช้ได้กับงานข้อความเช่นกัน ไม่ได้จำกัดแค่การคำนวณตัวเลข | โค้ดหลัก: `def format_receipt_line(item, price): return f"{item} ราคา {price} บาท"` เรียกซ้ำกับสินค้า 3 รายการ
3. แปลงองศาเซลเซียสเป็นฟาเรนไฮต์ ผิดพลาดเพราะไม่ทำ DRY (`celsius_to_fahrenheit_v1` vs `_v2`) — โดเมน: ตัวเลข/ข้อผิดพลาดที่พบบ่อย | สาธิตอะไร: การคัดลอกสูตรแทนการเรียกใช้ฟังก์ชันเดิมซ้ำ ทำให้พิมพ์ผิด (32 กลายเป็น 3) และผลลัพธ์ไม่ตรงกันทั้งที่ตั้งใจให้เหมือนกัน | โค้ดหลัก: `return celsius * 9/5 + 32` เทียบกับเวอร์ชันพิมพ์ผิด `return celsius * 9/5 + 3`

**Trick / จุดที่ต้องเน้น:**
- เขียนตรรกะการคำนวณไว้ที่เดียว แล้วนำกลับมาใช้ซ้ำได้เรื่อย ๆ แทนที่จะคัดลอกสูตรไปเขียนซ้ำหลายแห่ง — หากภายหลังต้องแก้สูตร ก็แก้เพียงจุดเดียว
- DRY ใช้ได้ผลทั้งกับโดเมนตัวเลข (เรขาคณิต) และโดเมนข้อความ (การจัดรูปแบบ) — ไม่ได้จำกัดอยู่แค่การคำนวณตัวเลขเท่านั้น
- ความเสี่ยงของการไม่ทำ DRY: เมื่อตรรกะเดียวกันถูกเขียนซ้ำหลายแห่ง การพิมพ์ผิดหรือแก้ไขในจุดหนึ่งจะไม่ส่งผลไปยังจุดอื่นโดยอัตโนมัติ ทำให้ตรรกะของโปรแกรมไม่สอดคล้องกัน
- Key Message จากสไลด์เดิม (Slide 1): "แตกปัญหาใหญ่เป็นฟังก์ชันย่อยที่อ่านง่ายกว่า"

## หัวข้อ 2: Function Definition กับ Function Call (ระดับ: พื้นฐาน)

**Subtopic / ประเด็นย่อยที่ควรพูดถึง:**
- การใช้งานฟังก์ชันแบ่งเป็นสองขั้นตอนที่แยกจากกันอย่างชัดเจน: definition และ call
- Function definition: การบอกโปรแกรมว่าฟังก์ชันนี้ชื่ออะไร รับข้อมูลอะไรเข้ามา มีคำสั่งอะไรอยู่ภายใน — เป็นเพียงการ "ประกาศ" ไว้เท่านั้น
- คำสั่งภายในฟังก์ชันจะยังไม่ถูกรันจนกว่าจะถูกเรียกใช้
- Function call: จุดที่โปรแกรมกระโดดเข้าไปรันคำสั่งภายในฟังก์ชันนั้นจริง ๆ
- ฟังก์ชันหนึ่งนิยามได้เพียงครั้งเดียว แต่เรียกใช้ได้หลายครั้งตามต้องการ
- ความเข้าใจผิดที่พบบ่อยของผู้เริ่มต้น: คิดว่าเพียงนิยามฟังก์ชันไว้ โปรแกรมจะรันคำสั่งภายในให้อัตโนมัติ ซึ่งไม่จริง
- ไวยากรณ์ Python: นิยามด้วย `def ชื่อฟังก์ชัน():` ตามด้วยกลุ่มคำสั่งเยื้อง (indent); เรียกใช้ด้วยชื่อฟังก์ชันตามด้วยวงเล็บ `()`

**ตัวอย่างที่ควรใช้ในสไลด์:**
1. ทักทาย (`greet`) เรียกซ้ำสองครั้ง — โดเมน: ข้อความพื้นฐาน | สาธิตอะไร: นิยามครั้งเดียว (บรรทัด def ยังไม่รัน) แต่เรียกใช้ได้หลายครั้ง แต่ละครั้งรันโค้ดจริง | โค้ดหลัก: `def greet(): print("สวัสดี")` แล้วเรียก `greet()` สองครั้ง คั่นด้วย print ก่อน-หลัง
2. ยกกำลังสองตัวเลขในลิสต์ผ่านลูป (`square`) — โดเมน: ตัวเลข/ลิสต์ | สาธิตอะไร: การเรียกฟังก์ชันเดิมซ้ำไม่จำเป็นต้องพิมพ์ชื่อฟังก์ชันด้วยมือทีละครั้ง แต่เรียกซ้ำอัตโนมัติผ่าน `for` loop ได้ | โค้ดหลัก: `def square(number): return number * number` เรียกใน `for n in numbers: print(square(n))`
3. นิยามฟังก์ชันแล้วลืมเรียกใช้ (`show_message`) — โดเมน: ข้อผิดพลาดที่พบบ่อย | สาธิตอะไร: การนิยามฟังก์ชันไม่ทำให้โค้ดข้างในรันเอง ถ้าไม่มีบรรทัดเรียกใช้ ฟังก์ชันจะไม่ทำงานเลย | โค้ดหลัก: `def show_message(): print("ทำงานแล้ว")` — ไม่มี `show_message()` ปรากฏในโปรแกรม output จึงไม่มีข้อความนั้น

**Trick / จุดที่ต้องเน้น:**
- ณ จุดนิยามฟังก์ชัน Python ยังไม่รันคำสั่ง `print`/คำสั่งใด ๆ ที่อยู่ภายใน มีเพียงการสร้างฟังก์ชันไว้ใช้งาน
- "การนิยาม" กับ "การเรียกใช้" เป็นคนละขั้นตอนกัน: นิยามเพียงครั้งเดียวแต่เรียกใช้ได้หลายครั้งตามต้องการ
- ข้อผิดพลาดที่พบบ่อยของผู้เริ่มต้น: เข้าใจผิดว่าการนิยามฟังก์ชัน (`def`) เพียงอย่างเดียวจะทำให้โค้ดภายในทำงานทันที — ความจริงต้องมีการเรียกใช้ (call) ด้วยชื่อฟังก์ชันตามด้วยวงเล็บเสมอ โปรแกรมจึงจะรันคำสั่งภายใน
- นักศึกษาต้องแยกให้ออกว่าบรรทัดที่มี `def` คือการนิยาม ส่วนบรรทัดที่เรียกชื่อฟังก์ชันตามด้วยวงเล็บคือการเรียกใช้ (สอดคล้อง Slide 2: ฟังก์ชัน `add` นิยามด้วย `def` แล้วเรียกด้วย `add(3, 5)`)

## หัวข้อ 3: Parameter กับ Argument (ระดับ: พื้นฐาน)

**Subtopic / ประเด็นย่อยที่ควรพูดถึง:**
- คำศัพท์สองคำที่มักถูกใช้ปะปนกัน: parameter (พารามิเตอร์) กับ argument (อาร์กิวเมนต์)
- Parameter: ชื่อตัวแปรที่ระบุไว้ในวงเล็บตอน "นิยาม" ฟังก์ชัน ทำหน้าที่เป็น "ช่องว่าง" ที่รอรับค่าเข้ามา ยังไม่มีค่าจริง
- Argument: ค่าจริงที่ถูกส่งเข้าไปตอน "เรียกใช้" ฟังก์ชัน ซึ่งถูกนำไปผูก (bind) กับพารามิเตอร์ตามลำดับตำแหน่งที่ปรากฏ
- Positional argument: วิธีส่งอาร์กิวเมนต์ตามลำดับตำแหน่ง — ตัวแรกผูกกับพารามิเตอร์ตัวแรกเสมอ ตัวที่สองผูกกับตัวที่สอง เรียงตามลำดับ
- ภาษาโปรแกรมส่วนใหญ่ไม่ตรวจสอบว่าค่าที่ส่งเข้ามาตรงกับความหมายที่พารามิเตอร์ต้องการหรือไม่ → การส่งอาร์กิวเมนต์ผิดลำดับเป็นข้อผิดพลาดที่พบบ่อยและตรวจจับได้ยาก
- ไวยากรณ์ Python: parameter ระบุในวงเล็บของ `def` เช่น `def introduce(name, age):`; argument คือค่าที่ส่งตอนเรียก เช่น `introduce("Aom", 20)`
- Keyword argument: การระบุชื่อพารามิเตอร์กำกับตอนเรียกใช้ ทำให้สลับลำดับการเขียนอาร์กิวเมนต์ได้โดยไม่เปลี่ยนความหมาย เพราะ Python ผูกค่าตามชื่อแทนตำแหน่ง
- เชื่อมโยงหัวข้ออื่น: แนวคิดนี้ถูกใช้ต่อในหัวข้อ 4 (ฟังก์ชัน `add(x, y)`) และต่อยอดในระดับกลาง (default parameters, `*args`/`**kwargs`)

**ตัวอย่างที่ควรใช้ในสไลด์:**
1. แนะนำตัวบุคคล (`introduce(name, age)`) — โดเมน: ข้อมูลบุคคล | สาธิตอะไร: พารามิเตอร์เป็นช่องว่างรอรับค่า อาร์กิวเมนต์คือค่าจริงที่ผูกตามลำดับตำแหน่งตอนเรียก | โค้ดหลัก: `def introduce(name, age): print(f"ฉันชื่อ {name} อายุ {age} ปี")` เรียก `introduce("Aom", 20)`, `introduce("Beam", 22)`
2. คำนวณราคารวม (`calculate_total(price, quantity)`) ด้วย positional vs keyword argument — โดเมน: การคำนวณราคาสินค้า | สาธิตอะไร: เปรียบเทียบ positional argument (`calculate_total(50, 3)`) กับ keyword argument (`calculate_total(quantity=3, price=50)`) ที่สลับลำดับได้เพราะระบุชื่อกำกับ ได้ผลลัพธ์เดียวกัน | โค้ดหลัก: `return price * quantity`
3. ส่งอาร์กิวเมนต์ผิดลำดับ (`introduce(20, "Aom")`) — โดเมน: ข้อผิดพลาดที่พบบ่อย | สาธิตอะไร: การสลับตำแหน่งอาร์กิวเมนต์ทำให้ค่าผูกผิดพารามิเตอร์โดยไม่มี error เตือน เป็นข้อผิดพลาดเชิงตรรกะที่ตรวจพบยาก | โค้ดหลัก: `introduce("Aom", 20)` (ถูก) เทียบกับ `introduce(20, "Aom")` (สลับ) ได้ output "ฉันชื่อ 20 อายุ Aom ปี"

**Trick / จุดที่ต้องเน้น:**
- Parameter คือชื่อตัวแปรที่รอรับค่า ยังไม่ใช่ค่าจริง ส่วน argument คือค่าจริงที่ถูกผูกเข้ากับพารามิเตอร์ตามลำดับตำแหน่งตอนเรียกใช้
- Keyword argument ทำให้สลับลำดับเขียนได้โดยไม่เปลี่ยนความหมาย เพราะ Python ผูกค่าตามชื่อพารามิเตอร์แทนตำแหน่งเมื่อระบุชื่อไว้ชัดเจน
- จุดที่ต้องเน้นที่สุด: Python จะไม่แจ้งข้อผิดพลาดใด ๆ เมื่อสลับลำดับ positional argument เพราะภาษาไม่ตรวจสอบชนิด/ความหมายของพารามิเตอร์ แต่จะผูกค่าตามตำแหน่งเสมอ — ผลลัพธ์จึงผิดเพี้ยนโดยที่โปรแกรมยังทำงานได้ตามปกติ (ไม่มี error หยุดโปรแกรม)
- สอดคล้อง Slide 2: "parameter รับค่าเข้า, return ส่งค่าออก" — ฟังก์ชัน `add(x, y)` มี `x`, `y` เป็นพารามิเตอร์ ส่วน `3`, `5` ใน `add(3, 5)` คืออาร์กิวเมนต์

## หัวข้อ 4: Return Value กับ Procedure (Void Function) (ระดับ: พื้นฐาน)

**Subtopic / ประเด็นย่อยที่ควรพูดถึง:**
- ฟังก์ชันแบ่งเป็นสองลักษณะตามพฤติกรรมการส่งผลลัพธ์กลับ
- ฟังก์ชันที่มีค่าที่ส่งกลับ (return value): ประมวลผลบางอย่างแล้วส่งผลลัพธ์กลับไปให้จุดที่เรียกใช้ นำไปเก็บในตัวแปรหรือใช้ในนิพจน์ต่อได้ทันที ทำได้ด้วยคำสั่ง `return`
- `return` เมื่อถูกรันจะหยุดการทำงานของฟังก์ชันทันทีและส่งค่าที่ระบุกลับไป
- ฟังก์ชันแบบ procedure (หรือ void function): ทำงานบางอย่าง (เช่น พิมพ์ข้อความ) แต่ไม่มีคำสั่ง `return` ที่ส่งค่ากลับให้ใช้งานต่อ
- ฟังก์ชันแบบ procedure ถูกเรียกใช้เพื่อ "ผลข้างเคียง" (side effect) ของมัน เช่นการแสดงผล ไม่ใช่เพื่อค่าที่ได้กลับมา
- พฤติกรรมสำคัญของ Python: หากฟังก์ชันไม่มีคำสั่ง `return` หรือมี `return` โดยไม่ระบุค่า ฟังก์ชันจะคืนค่าพิเศษ `None` กลับไปโดยอัตโนมัติเสมอ
- อันตราย: การนำผลลัพธ์จากฟังก์ชันแบบ procedure ไปใช้งานต่อราวกับว่ามันมีค่าที่ส่งกลับ จะได้ `None` แทนค่าที่ต้องการ
- ข้อกำหนดของคอร์สนี้: "return ค่าเดียวเสมอ" — ยังไม่สอน tuple unpacking / return หลายค่าพร้อมกัน ในระดับนี้

**ตัวอย่างที่ควรใช้ในสไลด์:**
1. เปรียบเทียบ `add(x, y)` (มี return) กับ `show_greeting(name)` (procedure) — โดเมน: คำนวณ vs ทักทาย | สาธิตอะไร: เก็บผลจาก `add` ได้ค่า 8 ใช้ต่อได้จริง ส่วนเก็บผลจาก `show_greeting` ได้ `None` เพราะไม่มี return | โค้ดหลัก: `def add(x,y): return x+y` เทียบ `def show_greeting(name): print(f"สวัสดี {name}")`
2. `find_max(numbers)` (มี return) กับ `print_list(items)` (procedure) บนลิสต์คะแนน — โดเมน: ประมวลผลลิสต์ | สาธิตอะไร: ยืนยันหลักการเดียวกับตัวอย่าง 4.1 แต่ในบริบทลิสต์ | โค้ดหลัก: `def find_max(numbers): return max(numbers)` เทียบ `def print_list(items): for item in items: print(item)`
3. เข้าใจผิดว่า procedure ส่งค่ากลับด้วย (`show_greeting` แล้วเอาไปต่อ string) — โดเมน: ข้อผิดพลาดที่พบบ่อย | สาธิตอะไร: การนำผลจากฟังก์ชัน procedure (ได้ `None`) ไปต่อกับ string เกิด `TypeError` | โค้ดหลัก: `message = show_greeting("Beam")` แล้ว `"ข้อความคือ: " + message` → `TypeError: can only concatenate str (not "NoneType") to str`

**Trick / จุดที่ต้องเน้น:**
- การเก็บผลจากฟังก์ชันที่มี `return` ได้ค่ามาใช้ต่อได้จริง ในขณะที่การเก็บผลจากฟังก์ชันแบบ procedure ได้ `None` เพราะฟังก์ชันที่ไม่มี `return` จะคืนค่า `None` โดยอัตโนมัติเสมอ
- ฟังก์ชันแบบ procedure ทำงานเป็น "ผลข้างเคียง" (side effect) เช่นพิมพ์ค่าออกมาทันทีตอนถูกเรียก แต่ค่าที่ถูกเก็บในตัวแปรปลายทางยังเป็น `None` อยู่ดี (ระวังสับสนระหว่าง "สิ่งที่พิมพ์ออกจอ" กับ "ค่าที่ return")
- ข้อผิดพลาดที่พบบ่อยที่สุด: เข้าใจผิดว่าฟังก์ชันที่พิมพ์ข้อความออกหน้าจอ (`print`) จะ "ส่งค่ากลับ" ข้อความนั้นให้ใช้งานต่อได้ด้วย — ความจริงคือ `print` ไม่ใช่ `return`
- `return` หยุด function ทันที (Key Message ของ Slide 3 ในสไลด์เดิม)
- กฎของวิชานี้: "return ค่าเดียวเสมอ" — ตัวอย่างทุกอันในหัวข้อนี้คืนค่าเดียวเสมอ (หรือ `None` โดยปริยาย)

## หัวข้อ 5: ขอบเขตตัวแปร (Scope) — Local กับ Global (ระดับ: พื้นฐาน)

**Subtopic / ประเด็นย่อยที่ควรพูดถึง:**
- Scope (ขอบเขต) ของตัวแปร: บริเวณของโปรแกรมที่ตัวแปรนั้นสามารถถูกอ้างถึงและใช้งานได้
- ตัวแปรเฉพาะที่ (local variable): ตัวแปรที่ถูกสร้างขึ้นภายในฟังก์ชัน มีขอบเขตจำกัดเฉพาะภายในฟังก์ชันนั้น
- เมื่อฟังก์ชันทำงานเสร็จสิ้น ตัวแปรเฉพาะที่จะถูกทำลายไป ไม่สามารถอ้างถึงได้จากภายนอกฟังก์ชัน
- ตัวแปรส่วนกลาง (global variable): ตัวแปรที่ถูกสร้างขึ้นภายนอกฟังก์ชันทั้งหมด มีขอบเขตครอบคลุมทั้งโปรแกรม อ่านค่าได้จากทุกจุดรวมถึงจากภายในฟังก์ชัน
- การ "อ่าน" ค่าตัวแปรส่วนกลางจากภายในฟังก์ชัน: ทำได้โดยตรงโดยไม่ต้องประกาศอะไรเพิ่มเติม
- การ "แก้ไข" ค่าตัวแปรส่วนกลางจากภายในฟังก์ชัน: จำเป็นต้องประกาศชื่อตัวแปรด้วยคำสั่ง `global` ก่อน
- หากไม่ประกาศ `global`: ภาษาโปรแกรมจะตีความว่ากำลังสร้างตัวแปรเฉพาะที่ตัวใหม่ขึ้นมาแทน — เป็นแหล่งความเข้าใจผิดที่พบบ่อยที่สุดข้อหนึ่งของผู้เริ่มต้น
- เชื่อมโยงหัวข้ออื่น: พารามิเตอร์ทุกตัว (หัวข้อ 3) เป็นตัวแปรเฉพาะที่ชนิดหนึ่งเสมอ
- หมายเหตุเวอร์ชัน Python: ข้อความ error `cannot access local variable ... where it is not associated with a value` เป็นรูปแบบของ Python 3.11+; เวอร์ชันเก่ากว่าจะขึ้น `local variable 'x' referenced before assignment` แต่ประเภท error (`UnboundLocalError`) เหมือนเดิม

**ตัวอย่างที่ควรใช้ในสไลด์:**
1. ยอดเงินคงเหลือ (`balance`, `deposit`, `show_balance`) — โดเมน: การเงิน/ตัวเลข | สาธิตอะไร: อ่านค่า global ได้อิสระโดยไม่ต้องประกาศ แต่ต้องประกาศ `global` ก่อนจึงจะแก้ไขได้ | โค้ดหลัก: `def deposit(amount): global balance; balance = balance + amount`
2. สถานะเกม (`game_status`, `update_status`, `show_status`) — โดเมน: ข้อความ (string) ไม่ใช่ตัวเลข | สาธิตอะไร: แนวคิด scope ใช้ได้กับตัวแปรชนิดข้อความเช่นเดียวกับตัวเลข | โค้ดหลัก: `def update_status(new_status): global game_status; game_status = new_status`
3. ลืมประกาศ `global` ก่อนแก้ไข (`deposit_wrong`) — โดเมน: ข้อผิดพลาดที่พบบ่อยที่สุดเรื่อง scope | สาธิตอะไร: ไม่ประกาศ `global` ทำให้ Python สร้างตัวแปร local ใหม่ทั้งฟังก์ชัน เกิด `UnboundLocalError` | โค้ดหลัก: `def deposit_wrong(amount): balance = balance + amount` (ไม่มี `global`) → `UnboundLocalError`

**Trick / จุดที่ต้องเน้น:**
- ฟังก์ชันอ่านตัวแปรส่วนกลางได้โดยตรง แต่การแก้ไขค่าตัวแปรส่วนกลางจากภายในฟังก์ชันจำเป็นต้องประกาศ `global` ก่อนเสมอ มิฉะนั้น Python จะตีความว่ากำลังสร้างตัวแปรเฉพาะที่ตัวใหม่แทน
- **Trick สำคัญที่สุด**: การมีการกำหนดค่า (assign) ให้ชื่อตัวแปรใด ๆ ภายในฟังก์ชัน — แม้เพียงจุดเดียว — จะทำให้ Python ถือว่าชื่อนั้นเป็นตัวแปรเฉพาะที่ตลอดทั้งฟังก์ชัน (ไม่ใช่แค่หลังจุดที่ assign) แม้แต่ตอนอ่านค่าฝั่งขวาของเครื่องหมาย `=` ก็ยังไม่มีค่าให้อ่าน จึงเกิด `UnboundLocalError`
- ตัวแปร global ที่พยายามแก้ไขโดยไม่ประกาศ `global` จะไม่ถูกแก้ไขจริง เพราะฟังก์ชันไม่สามารถทำงานจนจบได้
- Key Message จากสไลด์เดิม (Slide 5): "ตัวแปรใน function ไม่กระทบตัวแปรข้างนอก"
- คำสั่ง `global` เป็นการขยายความเพิ่มเติมจากสไลด์เดิม (สไลด์เดิมแสดงเฉพาะกรณีอ่านค่า)

## หัวข้อ 6: By Value vs By Reference (กลไกการส่งค่าให้ฟังก์ชันของ Python) (ระดับ: กลาง)

**Subtopic / ประเด็นย่อยที่ควรพูดถึง:**
- ภาษาโปรแกรมทั่วไปแบ่งกลไกการส่งอาร์กิวเมนต์เป็น 2 แบบหลัก: pass by value กับ pass by reference
- Python ใช้กลไกเฉพาะตัวคือ pass-by-object-reference: พารามิเตอร์ได้รับ "การอ้างอิง" ไปยังอ็อบเจกต์เดียวกับตัวแปรต้นทาง ไม่ใช่สำเนาข้อมูลทั้งก้อน
- พฤติกรรมที่สังเกตได้จริงขึ้นอยู่กับว่าอ็อบเจกต์เป็น mutable หรือ immutable ไม่ได้ขึ้นอยู่กับกลไกส่งค่าที่ต่างกัน
- immutable types (int, str, tuple): การกำหนดค่าใหม่ให้พารามิเตอร์ภายในฟังก์ชันจะสร้างอ็อบเจกต์ใหม่ขึ้นมา ไม่กระทบตัวแปรต้นทาง พฤติกรรมจึงดูคล้าย pass by value
- mutable types (list, dict, set): การเรียกเมธอดที่แก้ไขอ็อบเจกต์แบบ in-place (เช่น append) จะกระทบตัวแปรต้นทางด้วย เพราะพารามิเตอร์และตัวแปรต้นทางชี้ไปยังอ็อบเจกต์เดียวกันในหน่วยความจำ
- เชื่อมโยงกับหัวข้อ scope และ parameter/argument: ตัวแปร local ในฟังก์ชันเป็นเพียง "ชื่อ" ที่ชี้ไปยังอ็อบเจกต์ ไม่ใช่ช่องความจำแยกต่างหากเสมอไป — กฎเรื่อง scope ยังคงจริงอยู่เสมอ

**ตัวอย่างที่ควรใช้ในสไลด์:**
1. ส่งค่าชนิด immutable (int) — โดเมน: ตัวเลข | สาธิตอะไร: การกำหนดค่าใหม่ให้พารามิเตอร์ int ภายในฟังก์ชันไม่กระทบตัวแปรต้นฉบับภายนอก | โค้ดหลัก: `def change_value(x): x = x + 10` แล้วเรียก `change_value(num)` โดย `num = 5` — `num` ยังเป็น 5 นอกฟังก์ชัน
2. ส่งค่าชนิด mutable (list) — โดเมน: รายการ/list | สาธิตอะไร: การเรียกเมธอด in-place (append) กับพารามิเตอร์ list จะกระทบตัวแปรต้นฉบับภายนอกด้วย | โค้ดหลัก: `def add_item(items): items.append("B")` แล้วเรียกด้วย `my_list = ["A"]` — `my_list` กลายเป็น `['A', 'B']`
3. ส่งค่าชนิดข้อความ (str) — โดเมน: ข้อความ | สาธิตอะไร: str เป็น immutable เช่นเดียวกับ int พฤติกรรม "คล้าย pass by value" ครอบคลุม immutable ทุกชนิด | โค้ดหลัก: `def shout(message): message = message.upper()` เรียกด้วย `greeting_text = "hello world"` — `greeting_text` นอกฟังก์ชันยังเป็นตัวพิมพ์เล็กเหมือนเดิม

**Trick / จุดที่ต้องเน้น:**
- กลไกเบื้องหลังเป็น "pass-by-object-reference" แบบเดียวกันทั้งหมด ไม่ว่าจะเป็น mutable หรือ immutable — สิ่งที่ต่างกันคือพฤติกรรมที่สังเกตเห็น ไม่ใช่กลไกการส่งค่า
- immutable (int, str, tuple): กำหนดค่าใหม่ = สร้างอ็อบเจกต์ใหม่ ไม่กระทบต้นฉบับ
- mutable (list, dict, set): เมธอดที่แก้ไขแบบ in-place กระทบต้นฉบับ เพราะชี้ไปยังอ็อบเจกต์เดียวกัน
- หัวข้อนี้ไม่ปรากฏใน `slides/06_function.md` ต้นฉบับ — ถือเป็นเนื้อหาเสริมนอกขอบเขตสอบ
- ตัวอย่างในหัวข้อนี้ไม่มี return หลายค่า จึงไม่ขัดกับกฎ "return ค่าเดียวเสมอ"

## หัวข้อ 7: อาร์กิวเมนต์ค่าเริ่มต้น (Default Parameters) (ระดับ: กลาง)

**Subtopic / ประเด็นย่อยที่ควรพูดถึง:**
- นิยาม: default argument คือค่าที่กำหนดไว้ล่วงหน้าให้พารามิเตอร์ตอนนิยามฟังก์ชัน ทำให้เรียกฟังก์ชันได้โดยไม่ต้องระบุอาร์กิวเมนต์สำหรับพารามิเตอร์นั้นก็ได้
- ถ้าผู้เรียกไม่ส่งค่ามา ใช้ค่าเริ่มต้นอัตโนมัติ ถ้าส่งค่ามา ค่านั้นแทนที่ค่าเริ่มต้น
- ประโยชน์: ทำให้พารามิเตอร์บางตัวกลายเป็น "ทางเลือก" (optional) เพิ่มความยืดหยุ่นของฟังก์ชัน
- กฎการนิยาม: พารามิเตอร์ที่ไม่มีค่าเริ่มต้นต้องมาก่อนพารามิเตอร์ที่มีค่าเริ่มต้นเสมอ
- ข้อควรระวังเฉพาะของ Python: ค่าเริ่มต้นถูกสร้างขึ้น "เพียงครั้งเดียว" ตอนประมวลผลคำสั่ง `def` ไม่ใช่ทุกครั้งที่ฟังก์ชันถูกเรียก
- ผลจากข้อควรระวังข้างต้น: ถ้าค่าเริ่มต้นเป็น mutable (list, dict) จะก่อพฤติกรรมไม่คาดคิด (ค่าค้างข้ามการเรียก)
- วิธีแก้มาตรฐาน: กำหนดค่าเริ่มต้นเป็น `None` แล้วสร้างอ็อบเจกต์ mutable ใหม่ภายในฟังก์ชันเมื่อตรวจพบว่าไม่มีการส่งค่ามา
- Python รักษาชนิดข้อมูล (type) ตามอาร์กิวเมนต์ที่ส่งเข้ามาจริง ไม่ได้ยึดตามชนิดของค่าเริ่มต้นเสมอไป
- อาร์กิวเมนต์ส่งได้ทั้งแบบตามตำแหน่งและแบบระบุชื่อ เพื่อทับค่าเริ่มต้น

**ตัวอย่างที่ควรใช้ในสไลด์:**
1. พารามิเตอร์พร้อมค่าเริ่มต้น — โดเมน: ข้อความทักทาย | สาธิตอะไร: การเรียกโดยไม่ระบุอาร์กิวเมนต์จะใช้ค่าเริ่มต้น ระบุมาจะทับค่าเริ่มต้น | โค้ดหลัก: `def greet(name, greeting="สวัสดี")` — `greet("อาทิตย์")` ให้ `สวัสดี อาทิตย์`
2. ค่าเริ่มต้นแบบ mutable ที่ก่อปัญหา และวิธีแก้ — โดเมน: ตะกร้าสินค้า/list | สาธิตอะไร: mutable default argument ทำให้ค่าค้างข้ามการเรียกฟังก์ชัน และวิธีแก้ด้วย `None` sentinel | โค้ดหลัก: ผิด — `def add_item_bad(item, basket=[])`; ถูก — `def add_item_good(item, basket=None): if basket is None: basket = []`
3. คำนวณราคารวมพร้อมภาษี — โดเมน: การคำนวณเชิงธุรกิจ | สาธิตอะไร: default argument ใช้ได้ทั้งไม่ระบุ/ตามตำแหน่ง/keyword พร้อมชี้ว่า type ของผลลัพธ์ขึ้นกับอาร์กิวเมนต์จริง | โค้ดหลัก: `def calculate_total(price, tax_rate=0.07)` — `calculate_total(200, tax_rate=0)` → 200 (int ไม่ใช่ float)

**Trick / จุดที่ต้องเน้น:**
- ค่าเริ่มต้นถูกสร้าง "ครั้งเดียว" ตอน `def` ประมวลผล ไม่ใช่ทุกครั้งที่เรียกฟังก์ชัน — เป็นต้นตอของบั๊ก mutable default argument
- "Mutable default argument จะค้างค่าข้ามการเรียกฟังก์ชัน" — list/dict ว่างที่เป็นค่าเริ่มต้นผูกกับตัวฟังก์ชันเอง ไม่ได้สร้างใหม่ทุกครั้ง
- วิธีแก้มาตรฐานที่ต้องจำ: `basket=None` แล้วเช็ค `if basket is None: basket = []` ภายในฟังก์ชัน
- ผลลัพธ์ type ขึ้นกับอาร์กิวเมนต์ที่ส่งจริง ไม่ใช่ type ของค่า default
- หัวข้อนี้ไม่ปรากฏในสไลด์ 7 แผ่นต้นฉบับ ถือเป็นเนื้อหาเสริมนอกขอบเขตสอบ ไม่ขัดกับกฎ "return ค่าเดียวเสมอ"

## หัวข้อ 8: อาร์กิวเมนต์จำนวนไม่จำกัด (*args / **kwargs) (ระดับ: กลาง)

**Subtopic / ประเด็นย่อยที่ควรพูดถึง:**
- ปัญหาที่แก้: บางครั้งผู้ออกแบบฟังก์ชันไม่ทราบล่วงหน้าว่าผู้เรียกจะส่งอาร์กิวเมนต์เข้ามากี่ตัว
- แนวคิด arbitrary arguments แบ่งเป็น 2 รูปแบบ: (1) อาร์กิวเมนต์ตามตำแหน่งจำนวนไม่จำกัด — รวบรวมเป็น tuple ผ่านสัญลักษณ์ `*` (2) อาร์กิวเมนต์แบบระบุชื่อจำนวนไม่จำกัด — รวบรวมเป็น dict ผ่านสัญลักษณ์ `**`
- ธรรมเนียมการตั้งชื่อคือ `*args` และ `**kwargs` แต่ในทางเทคนิคตั้งชื่ออื่นได้ — ตัวสัญลักษณ์ `*`/`**` ต่างหากที่กำหนดพฤติกรรม
- กฎการเรียงลำดับพารามิเตอร์เมื่อใช้ร่วมกัน: พารามิเตอร์ปกติ → `*args` → `**kwargs` เป็นลำดับสุดท้ายเสมอ
- เชื่อมโยงกับหัวข้อ return value vs procedure (หัวข้อ 4) และ default parameters (หัวข้อ 7)

**ตัวอย่างที่ควรใช้ในสไลด์:**
1. `*args` รวบรวมอาร์กิวเมนต์ตามตำแหน่งจำนวนไม่จำกัด — โดเมน: คำนวณผลรวมตัวเลข | สาธิตอะไร: ฟังก์ชันเดียวเรียกด้วยจำนวนอาร์กิวเมนต์ต่างกันได้ | โค้ดหลัก: `def total(*numbers): ... for n in numbers: result += n`
2. ผสม `*args` กับ `**kwargs` ในฟังก์ชันเดียว — โดเมน: รายงานผลการเรียนนักเรียน | สาธิตอะไร: รับได้ทั้งพารามิเตอร์ปกติ + ตามตำแหน่งไม่จำกัด + ระบุชื่อไม่จำกัดพร้อมกัน | โค้ดหลัก: `def student_report(name, *subjects, **details)`
3. ออกใบเสร็จร้านอาหารด้วย `*args` และ `**kwargs` — โดเมน: ธุรกิจร้านอาหาร | สาธิตอะไร: จำลองสถานการณ์จริงที่จำนวนรายการ/ตัวเลือกเสริมไม่แน่นอน รวมถึงการวนลูปอ่าน `**kwargs` ด้วย `.items()` | โค้ดหลัก: `def print_receipt(customer, *items, **options): ... for key, value in options.items(): ...`

**Trick / จุดที่ต้องเน้น:**
- ชื่อ `args`/`kwargs` เป็นเพียงธรรมเนียม ไม่ใช่คำสงวน — `*` และ `**` ต่างหากที่ทำให้เกิดพฤติกรรมรวบรวมอาร์กิวเมนต์
- ลำดับการนิยามต้องเป็น: พารามิเตอร์ปกติ → `*args` → `**kwargs` เสมอ ห้ามสลับ
- `*args` เก็บเป็น tuple, `**kwargs` เก็บเป็น dict — เข้าถึงต่างกัน
- อาร์กิวเมนต์ตามตำแหน่งที่เกินจากพารามิเตอร์ปกติจะถูกจัดสรรเข้า `*args` โดยอัตโนมัติ ส่วน keyword ทั้งหมดเข้า `**kwargs` โดยอัตโนมัติ
- หัวข้อนี้ไม่ปรากฏในสไลด์ 7 แผ่นต้นฉบับ ถือเป็นเนื้อหาเสริมนอกขอบเขตสอบ ไม่ขัดกับกฎ "return ค่าเดียวเสมอ"

## หัวข้อ 9: การเรียกซ้ำ (Recursion) (ระดับ: กลาง)

**Subtopic / ประเด็นย่อยที่ควรพูดถึง:**
- นิยาม: recursion คือเทคนิคที่ฟังก์ชันหนึ่งเรียกใช้ตัวเองภายในนิยามของมันเอง เพื่อแก้ปัญหาที่แบ่งย่อยเป็นปัญหาย่อยลักษณะเดียวกันแต่ขนาดเล็กลงเรื่อย ๆ
- เป็นทางเลือกหนึ่งของการวนลูป (loop)
- องค์ประกอบสำคัญที่ต้องมีเสมอ 2 ส่วน: (1) กรณีฐาน (base case) (2) กรณีเรียกซ้ำ (recursive case)
- ผลจากการขาดกรณีฐาน: ฟังก์ชันเรียกตัวเองไม่มีที่สิ้นสุด
- ข้อจำกัดทางปฏิบัติ: call stack มีขีดจำกัด เมื่อลึกเกินจะเกิด error — ใน Python คือ `RecursionError: maximum recursion depth exceeded` (ขีดจำกัดเริ่มต้นประมาณ 1000 ระดับ)
- แนวคิดเรื่องการ "คลี่" (unwind) call stack กลับหลังถึงกรณีฐาน — แต่ละ call ที่ค้างอยู่จะทยอยคืนค่ากลับตามลำดับย้อนกลับ
- เชื่อมโยงกับ return value vs procedure (หัวข้อ 4) และ scope (หัวข้อ 5): แต่ละ call มีตัวแปร local แยกจากกันคนละ scope แม้เป็นฟังก์ชันเดียวกัน

**ตัวอย่างที่ควรใช้ในสไลด์:**
1. หาค่าแฟกทอเรียลด้วยการเรียกซ้ำ — โดเมน: คณิตศาสตร์ | สาธิตอะไร: รูปแบบมาตรฐานของ recursion ที่มี base case และ recursive case ชัดเจน | โค้ดหลัก: `def factorial(n): if n==0: return 1; else: return n * factorial(n-1)` — `factorial(4)` → 24
2. ฟังก์ชันเรียกซ้ำที่ขาดกรณีฐาน แล้วแก้ไข — โดเมน: นับถอยหลัง | สาธิตอะไร: ผลลัพธ์จริงเมื่อไม่มี base case (RecursionError) เทียบกับฟังก์ชันที่แก้ไขแล้วถูกต้อง | โค้ดหลัก: ผิด — `countdown_broken(n)` (ไม่มี base case) → `RecursionError`; ถูก — `countdown_fixed(n)` มี `if n==0: return`
3. กลับข้อความด้วยการเรียกซ้ำ — โดเมน: ข้อความ/string | สาธิตอะไร: recursion ใช้ได้กับโดเมนข้อมูลประเภทข้อความ | โค้ดหลัก: `def reverse_text(text): if len(text)==0: return text; else: return reverse_text(text[1:]) + text[0]` — `reverse_text("Python")` → `"nohtyP"`

**Trick / จุดที่ต้องเน้น:**
- "Recursion ต้องมี base case ไม่งั้นจะเรียกตัวเองไม่มีที่สิ้นสุดและเกิด RecursionError" — กรณีฐานไม่ใช่ทางเลือก แต่เป็นส่วนที่ขาดไม่ได้
- ตัวอย่าง `countdown_broken` เป็นการรันจริง — ค่า `n` ลดลงเรื่อย ๆ จนเกิน call stack limit แล้ว traceback แสดง `RecursionError: maximum recursion depth exceeded while calling a Python object`
- แต่ละ call ในการเรียกซ้ำมีตัวแปร parameter ของตัวเองแยก scope กัน
- การคืนค่ากลับ (unwind) เกิดขึ้นตามลำดับย้อนกลับหลังถึง base case — ควรมี diagram call stack เข้า-ออก เพราะเป็นจุดที่ผู้เรียนสับสนบ่อย
- recursion ไม่ได้ถูกสอนในสไลด์ 7 แผ่นต้นฉบับเลยแม้แต่แผ่นเดียว ถือเป็นเนื้อหาเสริมนอกขอบเขตสอบทั้งหมด ไม่ขัดกับกฎ "return ค่าเดียวเสมอ"

---

# ระดับสูง (หัวข้อ 10–15) — เนื้อหาเสริม นอกขอบเขตสอบ

## หัวข้อ 10: ฟังก์ชันชั้นหนึ่ง (First-class functions) (ระดับ: สูง)

**Subtopic / ประเด็นย่อยที่ควรพูดถึง:**
- นิยาม: ภาษาที่ถือว่าฟังก์ชันเป็น "ชั้นหนึ่ง" (first-class) คือฟังก์ชันถูกปฏิบัติเหมือนค่าข้อมูลชนิดอื่นทุกประการ
- คุณสมบัติ 4 อย่างที่ตามมา: (1) เก็บไว้ในตัวแปรได้ (2) ส่งเป็นอาร์กิวเมนต์ให้ฟังก์ชันอื่นได้ (3) เก็บไว้ในโครงสร้างข้อมูลได้ (4) ส่งกลับออกมาจากฟังก์ชันอื่นได้
- ตรงข้ามกับภาษาที่ฟังก์ชันเป็นเพียง "หน่วยคำสั่ง" เรียกได้อย่างเดียว
- first-class function เป็นรากฐานของ higher-order function (หัวข้อ 12)
- ใน Python ฟังก์ชันทุกตัวคือ `function` object โดยธรรมชาติ ไม่ต้องเปิดใช้งานพิเศษ

**ตัวอย่างที่ควรใช้ในสไลด์:**
1. กำหนดฟังก์ชันให้ตัวแปร (`greet` / `say_hello`) — โดเมน: ฟังก์ชันทักทายทั่วไป | สาธิตอะไร: การเขียนชื่อฟังก์ชันโดยไม่มีวงเล็บคือการคัดลอก "ตัวอ้างอิงฟังก์ชัน" ไม่ใช่เรียกใช้งาน | โค้ดหลัก: `say_hello = greet` แล้ว `say_hello("มานะ")`; `say_hello == greet` → `True`
2. Dispatch table — โดเมน: เครื่องคิดเลขพื้นฐาน | สาธิตอะไร: เก็บฟังก์ชันเป็น value ใน dict แล้วค้นหา-เรียกใช้ตาม key เพื่อลด if/elif ยาว ๆ | โค้ดหลัก: `operations = {"+": add, "-": subtract, "*": multiply}` แล้ว `func = operations[op]; return func(a, b)`
3. ข้อควรระวัง — สับสนระหว่างอ้างอิงฟังก์ชันกับเรียกฟังก์ชัน (`get_score`) — โดเมน: ฟังก์ชันคำนวณคะแนนที่มี side effect | สาธิตอะไร: `correct_ref = get_score` vs `wrong_ref = get_score()` ให้ผลต่างกันโดยไม่มี error เตือน | โค้ดหลัก: `type(correct_ref)` → `<class 'function'>`, `type(wrong_ref)` → `<class 'int'>`

**Trick / จุดที่ต้องเน้น:**
- "ไม่มีวงเล็บ" = คัดลอกตัวอ้างอิงฟังก์ชัน ยังไม่มีการทำงานใด ๆ เกิดขึ้น ส่วน "มีวงเล็บ" = เรียกใช้งานทันทีและเก็บเฉพาะ "ค่าที่ส่งกลับ"
- ถ้าเขียนผิดพลาดโดยลืมหรือใส่วงเล็บผิดจุด โปรแกรมจะทำงานไม่ตรงกับที่ตั้งใจ **โดยไม่มี error แจ้งเตือนชัดเจน** — ดีบักยาก
- ใช้ `type()` เป็นเครื่องมือพิสูจน์ความแตกต่างระหว่างตัวอ้างอิงฟังก์ชันกับค่าที่ถูกเรียกไปแล้ว
- dispatch table คือการใช้ประโยชน์จริงของ first-class function เพื่อลดโค้ด if/elif ซ้ำซ้อน

**หมายเหตุขอบเขต:** เป็นเนื้อหาเสริม/นอกขอบเขตสอบ ต่อยอดจากหัวข้อ 2 และ 4 และเป็นพื้นฐานของหัวข้อ 12 ไม่มีตัวอย่างที่ขัดกับกฎ "return ค่าเดียวเสมอ"

---

## หัวข้อ 11: ฟังก์ชันนิรนาม (Anonymous function / Lambda) (ระดับ: สูง)

**Subtopic / ประเด็นย่อยที่ควรพูดถึง:**
- นิยาม: lambda คือฟังก์ชันขนาดเล็กที่ไม่มีชื่อในตัวเอง ใช้งานแบบสั้น ๆ โดยไม่ต้องประกาศแบบเต็มรูปแบบด้วย `def`
- ข้อจำกัดสำคัญ: บรรจุได้เพียง "นิพจน์เดียว" (single expression) เท่านั้น ค่าของนิพจน์นั้นถูกคืนกลับโดยอัตโนมัติ ไม่ต้องเขียน `return`
- ความแตกต่างจาก `def` เป็นเรื่อง "รูปแบบการเขียน" เท่านั้น — ในทางความหมายและการทำงาน lambda ก็คือฟังก์ชันชนิดหนึ่งเช่นเดียวกับ `def`
- นิยมใช้เมื่อฟังก์ชันมีตรรกะสั้นมาก ใช้ครั้งเดียวหรือไม่กี่ครั้ง โดยเฉพาะเมื่อส่งเป็นอาร์กิวเมนต์ให้ฟังก์ชันอันดับสูง เช่น `sorted()`, `map()`, `filter()`

**ตัวอย่างที่ควรใช้ในสไลด์:**
1. เปรียบเทียบ lambda กับฟังก์ชันมีชื่อ (`square` vs `square_def`) — โดเมน: ยกกำลังสอง | สาธิตอะไร: lambda กับ `def` ให้ผลลัพธ์เหมือนกันทุกประการ `type()` ยืนยันว่าเป็น `function` object ชนิดเดียวกัน | โค้ดหลัก: `square = lambda x: x ** 2`
2. lambda เป็นเกณฑ์จัดเรียงข้อมูล — โดเมน: จัดอันดับคะแนนนักเรียน | สาธิตอะไร: lambda เป็น "ฟังก์ชันเกณฑ์" ระยะสั้นที่ส่งเป็น argument `key=` | โค้ดหลัก: `sorted(students, key=lambda record: record[1], reverse=True)`
3. **⚠️ ข้อควรระวัง (ขัดกับกฎวิชานี้โดยเจตนา)** — lambda คืนค่าหลายค่าพร้อมกัน (`calc_both`) — โดเมน: คำนวณผลรวม+ผลคูณ | สาธิตอะไร: lambda คืนค่าเป็น tuple ได้เหมือนฟังก์ชันปกติ แต่ผู้เรียกต้องใช้ tuple unpacking แยกค่า | โค้ดหลัก: `calc_both = lambda a, b: (a + b, a * b)` แล้ว `total, product = calc_both(3, 4)`

**Trick / จุดที่ต้องเน้น:**
- lambda ≠ ฟังก์ชันชนิดพิเศษ — Python มองว่าเป็น "ฟังก์ชัน" ชนิดเดียวกับที่นิยามด้วย `def` ต่างกันแค่รูปแบบการเขียน
- กรณีใช้งานจริงที่พบบ่อยที่สุด: เป็น "ฟังก์ชันเกณฑ์" ระยะสั้นที่ส่งเป็นอาร์กิวเมนต์ให้ `sorted`/`map`/`filter`
- ตัวอย่างที่ 2 จงใจใช้การเข้าถึงด้วยดัชนี (`record[0]`, `record[1]`) แทน tuple unpacking เพื่อไม่ให้พึ่งพา syntax ที่ยังไม่สอนในคอร์สนี้
- **⚠️ ตัวอย่างที่ 3 คือกรณีขัดแย้งกับกฎวิชานี้โดยเจตนา**: แม้ทำงานได้ถูกต้องจริง แต่ขัดกับกฎ "return ค่าเดียวเสมอ" และใช้ tuple unpacking ซึ่งยังไม่สอนในสัปดาห์ 1–7 — ต้องมองเป็น "ข้อควรระวัง" ไม่ใช่แนวปฏิบัติที่แนะนำ หากต้องการผลลัพธ์สองค่าจริง แนวทางที่สอดคล้องกับกฎวิชานี้คือแยกเป็นสองฟังก์ชัน

**หมายเหตุขอบเขต:** เป็นเนื้อหาเสริม/นอกขอบเขตสอบ ต่อยอดจากหัวข้อ 2 และหัวข้อ 10 **สำคัญ: ตัวอย่างที่ 3 คือจุดเดียวในเอกสารทั้งหมดที่ระบุไว้อย่างชัดเจนว่า "ขัดกับกฎ return ค่าเดียวเสมอ ของ `slides/06_function.md` (Slide 6) โดยตรง"** มี callout box ⚠️ กำกับไว้ — ควรใส่ callout เดียวกันนี้ในสไลด์เพื่อไม่ให้ผู้เรียนสับสนกับกฎหลักของคอร์ส

## หัวข้อ 12: ฟังก์ชันอันดับสูง (Higher-order functions) (ระดับ: สูง)

**Subtopic / ประเด็นย่อยที่ควรพูดถึง:**
- นิยาม: higher-order function คือฟังก์ชันที่มีคุณสมบัติอย่างน้อยหนึ่งใน 2 อย่าง: (1) รับฟังก์ชันอื่นเป็นอาร์กิวเมนต์ หรือ (2) คืนค่าเป็นฟังก์ชันออกมา
- เป็นไปได้เพราะภาษาถือว่าฟังก์ชันเป็น first-class (หัวข้อ 10)
- เป็นเครื่องมือสำคัญของ functional programming — แยก "ตรรกะที่ทำซ้ำ" ออกจาก "การกระทำเฉพาะจุด" ทำให้โค้ดนำกลับมาใช้ซ้ำได้มากขึ้น
- Python มี built-in higher-order function ที่ใช้บ่อย: `map()` (แปลงทุกสมาชิก) และ `filter()` (คัดกรองสมาชิกที่ผ่านเงื่อนไข) — มักใช้ร่วมกับ lambda (หัวข้อ 11)

**ตัวอย่างที่ควรใช้ในสไลด์:**
1. ฟังก์ชันรับฟังก์ชันอื่นเป็นอาร์กิวเมนต์ (`apply_twice`) — โดเมน: บวกเลขซ้อนสองรอบ | สาธิตอะไร: ฟังก์ชันหนึ่งรับ "ฟังก์ชัน" เป็นพารามิเตอร์แล้วเรียกซ้อนกัน | โค้ดหลัก: `def apply_twice(func, value): return func(func(value))`
2. กรองและแปลงข้อมูลด้วย filter/map — โดเมน: คัดกรอง+ให้คะแนนพิเศษ | สาธิตอะไร: `filter`/`map` เป็น built-in higher-order function ที่รับ lambda เป็นอาร์กิวเมนต์ แทนการเขียน `for` loop เอง | โค้ดหลัก: `list(filter(lambda s: s >= 50, scores))`
3. ข้อควรระวัง — closure late binding (`make_multipliers_wrong` vs `_correct`) — โดเมน: สร้างฟังก์ชันคูณเลขในลูป | สาธิตอะไร: lambda ที่สร้างในลูปแล้วอ้างอิงตัวแปรลูปโดยตรงจะได้ค่าผิดเมื่อเรียกภายหลัง | โค้ดหลัก: ผิด — `funcs.append(lambda x: x * i)`; ถูก — `funcs.append(lambda x, factor=i: x * factor)`

**Trick / จุดที่ต้องเน้น:**
- `apply_twice` เป็น higher-order function เพราะรับฟังก์ชันอื่นเป็นอาร์กิวเมนต์ — ตัวมันเองไม่จำเป็นต้องรู้ล่วงหน้าว่าฟังก์ชันที่ส่งเข้ามาทำอะไร
- `filter`/`map` ช่วยให้ไม่ต้องเขียน loop `for` ซ้ำ ๆ ด้วยตนเอง
- **Trick สำคัญที่สุด (closure late binding)**: closure ของ Python จะอ้างอิงถึง **"ตัวแปร"** ไม่ใช่ **"ค่า ณ ขณะนั้น"** — ทุก lambda ที่สร้างในลูปเดียวกัน "จำ" ตัวแปรลูปตัวเดียวกัน เมื่อลูปจบ ทุกฟังก์ชันจึงใช้ค่าสุดท้ายเหมือนกันหมด (`[30, 30, 30]` แทนที่จะเป็น `[10, 20, 30]`)
- วิธีแก้ที่ถูกต้อง: กำหนดค่าปัจจุบันของตัวแปรลูปให้เป็น "ค่าเริ่มต้นของพารามิเตอร์" อีกตัวหนึ่งในนิยาม lambda เอง ซึ่งจะถูกประเมินและผูกไว้ทันทีตอนสร้างฟังก์ชันแต่ละตัว
- เชื่อมโยงโดยตรงกับแนวคิด scope (local vs global) ในหัวข้อ 5

**หมายเหตุขอบเขต:** เป็นเนื้อหาเสริม/นอกขอบเขตสอบ ต่อยอดจากหัวข้อ 5, หัวข้อ 10 และ 11 ไม่มีตัวอย่างที่ขัดกับกฎ "return ค่าเดียวเสมอ"

## หัวข้อ 13: ฟังก์ชันบริสุทธิ์ กับ ผลข้างเคียง (Pure function vs Side effect) (ระดับ: สูง)

**Subtopic / ประเด็นย่อยที่ควรพูดถึง:**
- นิยาม pure function: (1) เรียกด้วยอาร์กิวเมนต์ชุดเดียวกันแล้วได้ผลลัพธ์เดียวกันเสมอ (2) การทำงานไม่ก่อให้เกิดการเปลี่ยนแปลงใด ๆ ที่มองเห็นได้จากภายนอกขอบเขตของตัวเอง
- ตัวอย่างของ side effect: แก้ไขตัวแปรส่วนกลาง, แก้ไขข้อมูลที่รับเข้ามาเป็นอาร์กิวเมนต์, พิมพ์ข้อความ, เขียนไฟล์, ติดต่อแหล่งข้อมูลภายนอก
- ฟังก์ชันมี side effect ไม่ได้ผิดหรือใช้งานไม่ได้ — โปรแกรมจริงต้องมีส่วนแสดงผล/บันทึกข้อมูล/แก้ไขสถานะ
- ประโยชน์ของการแยก "ส่วนคำนวณบริสุทธิ์" ออกจาก "ส่วนมี side effect": ทดสอบง่ายขึ้น คาดเดาพฤติกรรมง่ายขึ้น นำกลับไปใช้ซ้ำได้ปลอดภัยกว่า
- หัวข้อนี้ไม่มีหน้าตรงในสามเว็บอ้างอิงหลัก (W3Schools/TutorialsPoint/GeeksforGeeks) เป็นแนวคิดวิศวกรรมซอฟต์แวร์ทั่วไปที่เสริมขึ้นเอง

**ตัวอย่างที่ควรใช้ในสไลด์:**
1. เปรียบเทียบ pure vs impure (`add_pure` vs `add_impure`) — โดเมน: บวกเลขสองจำนวน | สาธิตอะไร: pure function เรียกซ้ำด้วยอาร์กิวเมนต์เดิมได้ผลเดิมเสมอ impure function แก้ตัวแปร global และ print ควบคู่กับการคืนค่า | โค้ดหลัก: `add_pure(a,b): return a+b`
2. เหตุผลด้านการทดสอบ (testability) — โดเมน: คำนวณราคาหลังหักส่วนลด | สาธิตอะไร: pure function ทดสอบด้วย `assert` ได้ตรง ๆ ทันที | โค้ดหลัก: `assert calculate_discount(100, 10) == 90`
3. ข้อควรระวัง — ฟังก์ชันแก้ไขข้อมูลของผู้เรียกโดยไม่ตั้งใจ (`add_bonus_item`) — โดเมน: ตะกร้าสินค้า | สาธิตอะไร: การส่ง mutable object เป็นอาร์กิวเมนต์แล้วแก้ไขในฟังก์ชัน จะกระทบตัวแปรต้นฉบับของผู้เรียกด้วย | โค้ดหลัก: `cart.append("ของแถม"); return cart` — `new_cart is shopping_cart` → `True`

**Trick / จุดที่ต้องเน้น:**
- pure function เรียกกี่ครั้งด้วยอาร์กิวเมนต์ชุดเดิมก็ได้ผลลัพธ์เดิมเสมอ ส่วน impure function ทำให้ "ผลลัพธ์โดยรวมของโปรแกรมขึ้นกับลำดับการเรียกฟังก์ชัน"
- เหตุผลเชิงปฏิบัติที่นิยมแยกฟังก์ชัน "คำนวณ" ออกจากฟังก์ชัน "แสดงผล": ทดสอบด้วย `assert` ได้ทันทีโดยไม่ต้องกังวลข้อความที่พิมพ์ออกหน้าจอ
- **Trick สำคัญ (mutable argument aliasing)**: การส่ง list เข้าฟังก์ชันทำให้พารามิเตอร์ชี้ไปยัง object เดียวกันกับอาร์กิวเมนต์ (เชื่อมโยงหัวข้อ 6) — เมื่อฟังก์ชันเรียก `.append(...)` จึงแก้ไข object ต้นฉบับโดยตรง
- หากไม่ต้องการผลข้างเคียงแบบนี้ ควรสร้างลิสต์ใหม่ภายในฟังก์ชันแทน เช่น `return cart + ["ของแถม"]`

**หมายเหตุขอบเขต:** เป็นเนื้อหาเสริม/นอกขอบเขตสอบ และไม่มีแหล่งอ้างอิงตรงจากสามเว็บไซต์หลัก ต่อยอดจากหัวข้อ 5 และหัวข้อ 6 ไม่มีตัวอย่างที่ขัดกับกฎ "return ค่าเดียวเสมอ"

## หัวข้อ 14: Signature และสัญญาของฟังก์ชัน (Function signature / Contract) (ระดับ: สูง)

**Subtopic / ประเด็นย่อยที่ควรพูดถึง:**
- นิยาม signature: ส่วนหัวของฟังก์ชันที่ระบุชื่อฟังก์ชัน จำนวน/ชื่อพารามิเตอร์ที่รับเข้ามา และ (ถ้ามี) ชนิดของค่าที่คาดว่าจะส่งกลับ
- signature ทำหน้าที่เป็น "สัญญา" (contract) ระหว่างผู้เขียนฟังก์ชันกับผู้เรียกใช้ — ผู้เรียกทราบได้จาก signature อย่างเดียวว่าต้องส่งอาร์กิวเมนต์กี่ตัว ชนิดใด และควรได้รับอะไรกลับมา โดยไม่ต้องอ่านโค้ดภายใน
- สัญญาครอบคลุมมากกว่าชื่อพารามิเตอร์ — รวมถึง "ชนิด/ลักษณะของค่าที่ส่งกลับในทุกเส้นทางการทำงาน" ด้วย
- function annotation ใน Python: ระบุชนิดข้อมูลของพารามิเตอร์และค่าที่คืนไว้ใน signature ได้ แต่เพราะ Python เป็น dynamically typed จึงเป็นเพียง "เอกสารประกอบ" ไม่ได้ถูกบังคับตรวจสอบขณะรันจริง

**ตัวอย่างที่ควรใช้ในสไลด์:**
1. signature เป็นสัญญาที่ผู้เรียกใช้พึ่งพาได้ (`calculate_area`) — โดเมน: คำนวณพื้นที่สี่เหลี่ยม | สาธิตอะไร: ไม่ว่าจะเรียกแบบ positional หรือ keyword argument ผลลัพธ์ตรงตาม signature เสมอ | โค้ดหลัก: `calculate_area(5, 3)` เทียบ `calculate_area(height=3, width=5)` ให้ผล 15 เท่ากัน
2. function annotation บันทึกสัญญาไว้ใน signature — โดเมน: คำนวณพื้นที่ | สาธิตอะไร: annotation เป็นเอกสารประกอบเท่านั้น ไม่บังคับชนิดข้อมูลจริงขณะรัน | โค้ดหลัก: `def calculate_area(width: float, height: float) -> float:` แล้วดู `calculate_area.__annotations__`
3. ข้อควรระวัง — ละเมิดสัญญาโดยปริยายด้วยการคืนค่าไม่สอดคล้องกัน (`find_student`) — โดเมน: ค้นหาชื่อนักเรียนจาก id | สาธิตอะไร: ฟังก์ชันที่คืน string เมื่อเจอ แต่คืน `None` โดยปริยายเมื่อไม่เจอ ทำให้ผู้เรียกใช้เจอ `AttributeError` | โค้ดหลัก: `for record in records: if ...: return record["name"]` (ไม่มี return ท้ายฟังก์ชัน)

**Trick / จุดที่ต้องเน้น:**
- signature กำหนดว่าฟังก์ชัน "รับอะไรเข้า และคืนอะไรออก" โดยไม่ต้องอ่านโค้ดภายในฟังก์ชันเลย
- **annotation ไม่ใช่กลไกบังคับชนิดข้อมูล** — เป็นเพียงเอกสารประกอบที่มีประโยชน์หลักสำหรับผู้พัฒนาและ IDE/type-checker ภายนอก เก็บไว้ใน `__annotations__`
- **Trick สำคัญที่สุด**: ฟังก์ชันที่วนลูปค้นหาแล้วมี `return` เฉพาะกรณีเจอ (ไม่มี return ท้ายฟังก์ชัน) จะคืนค่า `None` โดยปริยาย (implicit return) โดยไม่มีคำเตือนใด ๆ — ผู้เรียกที่สมมติว่าได้ชนิดข้อมูลเดิมเสมอ จะพบ error ทันทีที่รันจริง (เช่น `AttributeError: 'NoneType' object has no attribute 'upper'`)
- "สัญญา" ของฟังก์ชันไม่ได้มีแค่ชื่อพารามิเตอร์ แต่รวมถึงชนิด/ลักษณะของค่าที่ส่งกลับในทุกเส้นทางการทำงานด้วย

**หมายเหตุขอบเขต:** เป็นเนื้อหาเสริม/นอกขอบเขตสอบ ต่อยอดจากหัวข้อ 3 และหัวข้อ 4 ไม่มีตัวอย่างที่ขัดกับกฎ "return ค่าเดียวเสมอ" — แต่ตัวอย่างที่ 3 เชื่อมโยงเชิงแนวคิดกับหลักการนี้ในแง่ที่ฟังก์ชันควรคืนค่าที่คาดเดาได้เสมอ

## หัวข้อ 15: หลักความรับผิดชอบเดียว (Single Responsibility Principle) (ระดับ: สูง)

**Subtopic / ประเด็นย่อยที่ควรพูดถึง:**
- นิยาม SRP: หน่วยของโค้ดหนึ่งหน่วย (ระดับฟังก์ชัน) ควรมี "เหตุผลให้ต้องเปลี่ยนแปลง" เพียงเหตุผลเดียวเท่านั้น
- กล่าวโดยง่าย: ฟังก์ชันหนึ่งฟังก์ชันควรทำหน้าที่เดียวให้ดี ไม่ควรรวมงานหลายอย่างที่ไม่เกี่ยวข้องกันไว้ในที่เดียว
- เชื่อมโยงโดยตรงกับ decomposition (หัวข้อ 1, Slide 4 ของ `slides/06_function.md`) — SRP ให้ "เกณฑ์" ที่ชัดเจนขึ้นว่าควรแบ่งฟังก์ชันตรงไหน
- ประโยชน์: ทดสอบได้ง่ายขึ้น แก้ไขส่วนหนึ่งโดยไม่กระทบอีกส่วนหนึ่ง นำกลับไปใช้ซ้ำในบริบทอื่นได้สะดวกขึ้น
- ไม่มีหน้าตรงในสามเว็บอ้างอิงหลัก เพราะเป็นหลักการออกแบบซอฟต์แวร์ ไม่ใช่ syntax เฉพาะภาษา

**ตัวอย่างที่ควรใช้ในสไลด์:**
1. แยกการคำนวณออกจากการแสดงผล (`process_order_bad` vs `calculate_total`+`display_total`) — โดเมน: คำนวณยอดสั่งซื้อ | สาธิตอะไร: ฟังก์ชันเดียวทำสองหน้าที่แยกทดสอบ/นำผลไปใช้ต่อไม่ได้ เทียบกับแยกตาม SRP | โค้ดหลัก: `process_order_bad(price, qty)` เทียบ `calculate_total` + `display_total` แยกกัน
2. ระบบคำนวณโบนัสการขายที่แยกความรับผิดชอบชัดเจน — โดเมน: คำนวณโบนัสพนักงานขาย | สาธิตอะไร: แยกเป็น 3 ฟังก์ชันคนละหน้าที่ (คำนวณ/บันทึกข้อมูล/จัดรูปแบบข้อความ) | โค้ดหลัก: `calculate_bonus(sales_amount)`, `record_sale(sales_amount)`, `format_bonus_message(bonus)`
3. ข้อควรระวัง — ฟังก์ชันที่ทำหลายหน้าที่จนนำกลับมาใช้ซ้ำไม่ได้ (`calculate_and_show_grade` vs `calculate_grade`) — โดเมน: ตัดสินเกรดจากคะแนน | สาธิตอะไร: ฟังก์ชันที่รวมตรรกะตัดสินใจ + แสดงผล ใช้กับ list comprehension ไม่ได้โดยไม่มีข้อความแทรกออกมา | โค้ดหลัก: `calculate_and_show_grade(score)` เทียบ `calculate_grade(score)` ใช้ใน `[calculate_grade(s) for s in [85,72,60]]`

**Trick / จุดที่ต้องเน้น:**
- ฟังก์ชันที่รวมสองหน้าที่ไว้ด้วยกันมี "เหตุผลให้ต้องแก้ไขมากกว่าหนึ่งอย่าง" และไม่สามารถนำส่วนคำนวณไปใช้ซ้ำได้โดยไม่พิมพ์ผลลัพธ์ออกมาด้วย
- แนวทางที่แยกฟังก์ชันมีความยืดหยุ่นในการนำไปใช้ซ้ำและทดสอบมากกว่า แม้ผลลัพธ์ที่ผู้ใช้เห็นจะเหมือนกันก็ตาม
- ตัวอย่างที่ 3 แสดง **ผลกระทบเชิงปฏิบัติที่จับต้องได้** ของการละเมิด SRP: หากนำฟังก์ชันที่มี `print` แทรกอยู่ไปใช้ใน list comprehension จะได้ข้อความพิมพ์แทรกกลางระหว่างการประมวลผลอย่างไม่ต้องการ
- เชื่อมโยงกับหัวข้อ 13 (pure function vs side effect) — ฟังก์ชันที่คำนวณอย่างเดียวไม่มีผลข้างเคียงใด ๆ จึงนำไปใช้ซ้ำได้อย่างปลอดภัย

**หมายเหตุขอบเขต:** เป็นเนื้อหาเสริม/นอกขอบเขตสอบ และไม่มีแหล่งอ้างอิงตรงจากสามเว็บไซต์หลัก ต่อยอดจากหัวข้อ 1, Slide 4 ของ `slides/06_function.md` และหัวข้อ 13 ไม่มีตัวอย่างที่ขัดกับกฎ "return ค่าเดียวเสมอ"

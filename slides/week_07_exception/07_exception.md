## Slide 2 — Exception คืออะไร ต่างจาก Syntax Error อย่างไร
**Key Message**: Syntax error ตรวจพบก่อนโปรแกรมเริ่มรัน ส่วน exception เกิดขึ้นระหว่างโปรแกรมกำลังทำงานจริง

- ข้อผิดพลาดในการเขียนโปรแกรมแบ่งได้ 2 ลักษณะตามช่วงเวลาที่ตรวจพบ: syntax error (ตรวจพบจากโครงสร้างคำสั่งเพียงอย่างเดียว ไม่ต้องรันโปรแกรมเลย) และ exception (เกิดขึ้นขณะโปรแกรมทำงานจริง)
- แนวคิดนี้เป็นแนวคิดทั่วไปของภาษาโปรแกรมสมัยใหม่ ไม่ผูกกับภาษาใดภาษาหนึ่ง
- ในไพทอน syntax error ถูกตรวจพบในขั้นตอน parsing ก่อนตัวแปลภาษาเริ่มประมวลผลคำสั่งใด ๆ — พบแล้วโปรแกรมจะไม่ทำงานแม้แต่บรรทัดเดียว (ตัวอย่างที่พบบ่อย: การเยื้องบรรทัดผิด รายงานเป็น `IndentationError` ซึ่งเป็นชนิดย่อยของ `SyntaxError`)
- exception เกิดขึ้นหลังโปรแกรมเริ่มทำงานไปแล้วระยะหนึ่ง เมื่อเกิดขึ้นไพทอนจะแสดง traceback หากไม่มีการดักจับ โปรแกรมจะหยุดทำงานทันทีที่บรรทัดนั้น คำสั่งถัดจากจุดเกิดข้อผิดพลาดจะไม่ถูกประมวลผลเลย

## Slide 4 — ตัวอย่าง 1.1: ค่าเฉลี่ยคะแนนสอบ (IndexError ที่ไม่ถูกดักจับ)
**Key Message**: เมื่อ exception ไม่ถูกดักจับ โปรแกรมหยุดทันที คำสั่งที่เหลือทั้งหมดจะไม่ถูกรันเลย

```python
print("เริ่มโปรแกรมคำนวณค่าเฉลี่ยคะแนนสอบ")
scores = [80, 90, 70]
total = sum(scores)
average = total / len(scores)
print("ค่าเฉลี่ยคือ", average)
print(scores[5])
print("บรรทัดนี้จะไม่ถูกรัน")
```

**Output:**
```
เริ่มโปรแกรมคำนวณค่าเฉลี่ยคะแนนสอบ
ค่าเฉลี่ยคือ 80.0
Traceback (most recent call last):
  File "exercise.py", line 6, in <module>
    print(scores[5])
          ~~~~~~^^^
IndexError: list index out of range
```

- บรรทัดหลังจุดเกิด `IndexError` ไม่ถูกรันเลยแม้จะเป็นเพียงคำสั่ง `print` ธรรมดา แสดงว่าเมื่อ exception เกิดขึ้นและไม่ถูกดักจับ การทำงานทั้งโปรแกรมจะหยุดทันที
- รายการ `scores` มีสมาชิก 3 ตัว การเรียก `scores[5]` จึงเกินขอบเขตดัชนีที่มีอยู่จริง ข้อผิดพลาดนี้ตรวจพบได้เฉพาะเมื่อโปรแกรมทำงานมาถึงบรรทัดนั้นจริง

## Slide 5 — ตัวอย่าง 1.2: ราคารวมสินค้าในตะกร้า (TypeError)
**Key Message**: ไพทอนไม่แปลงชนิดข้อมูลให้อัตโนมัติ การบวก `int` กับ `str` โดยตรงจึงเกิด `TypeError`

```python
print("เริ่มโปรแกรมคำนวณราคารวมของสินค้าในตะกร้า")
price = 150
shipping_fee = "50"
total_price = price + shipping_fee
print("ราคารวมคือ", total_price)
```

**Output:**
```
เริ่มโปรแกรมคำนวณราคารวมของสินค้าในตะกร้า
Traceback (most recent call last):
  File "exercise.py", line 4, in <module>
    total_price = price + shipping_fee
                  ~~~~~~^~~~~~~~~~~~~~
TypeError: unsupported operand type(s) for +: 'int' and 'str'
```

- `TypeError` เกิดจากการนำ `int` และ `str` มาบวกกันโดยตรง ไพทอนไม่แปลงชนิดข้อมูลให้อัตโนมัติ ข้อความ traceback ระบุชนิดข้อมูลทั้งสองฝั่งที่ขัดแย้งกันไว้ชัดเจน
- ต่างจากตัวอย่างที่ 1.1 ตรงที่ต้นเหตุคือชนิดข้อมูลไม่สอดคล้องกัน ไม่ใช่การเข้าถึงดัชนีเกินขอบเขต

## Slide 6 — ตัวอย่าง 1.3: ตรวจสอบอายุผู้สมัครสมาชิก (IndentationError)
**Key Message**: `IndentationError` เป็นชนิดย่อยของ `SyntaxError` ตรวจพบก่อนโปรแกรมเริ่มรัน จึงดักจับด้วย try/except ไม่ได้

```python
age = 20
    print("อายุคือ", age)
```

**Output:**
```
  File "exercise.py", line 2
    print("อายุคือ", age)
IndentationError: unexpected indent
```

- ไม่มีข้อความใดปรากฏบนหน้าจอเลยแม้แต่บรรทัดเดียว เพราะข้อผิดพลาดถูกตรวจพบตั้งแต่ขั้นตอนตรวจสอบไวยากรณ์ ก่อนโปรแกรมเริ่มทำงานจริง
- `IndentationError` ไม่ใช่ exception จึงไม่สามารถใช้ `try`/`except` ดักจับได้ เพราะโปรแกรมยังไม่ทันเริ่มทำงาน — ต่างจากตัวอย่างที่ 1.1/1.2 ที่โปรแกรมยังพิมพ์ข้อความบางส่วนได้ก่อนจะพบข้อผิดพลาด

## Slide 7 — สรุป: Syntax Error vs Exception
**Key Message**: จุดต่างที่สำคัญที่สุดคือ "ช่วงเวลาที่ตรวจพบ" ซึ่งกำหนดว่าดักจับด้วย try/except ได้หรือไม่

| ประเด็น | Syntax Error | Exception |
|---|---|---|
| ตรวจพบเมื่อใด | ก่อนโปรแกรมเริ่มทำงาน (ขั้นตอน parsing) | ระหว่างโปรแกรมทำงานจริง |
| ผลต่อการรัน | โปรแกรมไม่ทำงานแม้แต่บรรทัดเดียว | โปรแกรมทำงานไปแล้วบางส่วนก่อนหยุด |
| ดักจับด้วย try/except ได้หรือไม่ | ไม่ได้ | ได้ |
| ตัวอย่างที่พบบ่อย | `IndentationError` | `IndexError`, `TypeError`, `ValueError`, `ZeroDivisionError` |

## Slide 8 — try/except พื้นฐาน (จับ exception ประเภทเดียว)
**Key Message**: `try` คือบล็อกทดลองรัน `except` คือบล็อกรับมือ — เกิดปัญหาเมื่อไรกระโดดออกจาก try ทันที

- แนวคิดพื้นฐานคือแบ่งโค้ดเป็น 2 ส่วน: ส่วน "ทดลองรัน" คำสั่งที่อาจมีปัญหา และส่วน "รับมือ" เมื่อปัญหานั้นเกิดขึ้นจริง
- หากส่วนแรกทำงานสำเร็จ ส่วนที่สองจะไม่ถูกเรียกใช้เลย หากเกิดปัญหา การทำงานจะกระโดดออกจากส่วนแรกทันทีไปยังส่วนที่สอง คำสั่งที่เหลืออยู่ในส่วนแรกหลังจุดเกิดปัญหาจะไม่ถูกประมวลผลอีกเลย
- ในไพทอน เขียนด้วย `try` ตามด้วย `except` ระบุชื่อชนิดข้อผิดพลาดต่อท้าย
- เมื่อ `except` ทำงานเสร็จแล้ว โปรแกรมดำเนินต่อตามปกติ ไม่หยุดทำงานทั้งโปรแกรม

## Slide 10 — ตัวอย่าง 2.1: ปริมาณน้ำมันเฉลี่ยต่อถัง (ZeroDivisionError)
**Key Message**: โปรแกรมยังทำงานต่อได้ตามปกติหลังบล็อก except — นี่คือประโยชน์หลักของ try/except

```python
total_liters = 0
number_of_tanks = 0
try:
    average_per_tank = total_liters / number_of_tanks
    print("น้ำมันเฉลี่ยต่อถังคือ", average_per_tank, "ลิตร")
except ZeroDivisionError:
    print("ไม่สามารถคำนวณค่าเฉลี่ยได้ เนื่องจากจำนวนถังเป็นศูนย์")
print("โปรแกรมทำงานต่อไปได้ตามปกติ")
```

**Output:**
```
ไม่สามารถคำนวณค่าเฉลี่ยได้ เนื่องจากจำนวนถังเป็นศูนย์
โปรแกรมทำงานต่อไปได้ตามปกติ
```

- โปรแกรมยังคงทำงานได้ตามปกติหลังบล็อก except ต่างจากหัวข้อ 1 ที่โปรแกรมหยุดกลางคัน — นี่คือประโยชน์หลักของ `try`/`except`
- บรรทัดที่เหลือใน `try` หลังจุดเกิดข้อผิดพลาดก็ไม่ถูกรันเช่นกัน แม้จะมี `except` รองรับอยู่แล้วก็ตาม

---

## Slide 11 — ตัวอย่าง 2.2: ยืมหนังสือของห้องสมุด (ValueError)
**Key Message**: โครงสร้างเดียวกันดักจับข้อผิดพลาดคนละชนิดได้ เพียงเปลี่ยนชื่อชนิดหลัง except

```python
book_quantity_text = "ห้าเล่ม"
try:
    book_quantity = int(book_quantity_text)
    print("จำนวนหนังสือที่ยืมคือ", book_quantity, "เล่ม")
except ValueError:
    print("ข้อมูลจำนวนหนังสือไม่ถูกต้อง กรุณากรอกเป็นตัวเลข")
print("ระบบยืมหนังสือพร้อมรับคำสั่งถัดไป")
```

**Output:**
```
ข้อมูลจำนวนหนังสือไม่ถูกต้อง กรุณากรอกเป็นตัวเลข
ระบบยืมหนังสือพร้อมรับคำสั่งถัดไป
```

- ชนิดข้อผิดพลาดคือ `ValueError` ไม่ใช่ `ZeroDivisionError` แสดงว่าโครงสร้างเดียวกันดักจับข้อผิดพลาดคนละชนิดได้ เพียงเปลี่ยนชื่อชนิดหลัง `except`
- ฟังก์ชัน `int(...)` เป็นจุดที่มักเกิด `ValueError` บ่อยที่สุดในโปรแกรมที่รับข้อมูลจากผู้ใช้

---

## Slide 12 — ตัวอย่าง 2.3: พยากรณ์อากาศรายวัน (IndexError, edge case)
**Key Message**: ดัชนีที่เกินจำนวนสมาชิกจริงในรายการ ทำให้เกิด IndexError เสมอ

```python
weekly_temperatures = [31, 32, 30, 29]
try:
    friday_temperature = weekly_temperatures[4]
    print("อุณหภูมิวันศุกร์คือ", friday_temperature, "องศาเซลเซียส")
except IndexError:
    print("ไม่มีข้อมูลอุณหภูมิของวันที่ระบุ")
print("ระบบพยากรณ์อากาศทำงานต่อไปได้ตามปกติ")
```

**Output:**
```
ไม่มีข้อมูลอุณหภูมิของวันที่ระบุ
ระบบพยากรณ์อากาศทำงานต่อไปได้ตามปกติ
```

- `IndexError` เกิดจากความไม่สอดคล้องระหว่างจำนวนสมาชิกจริง (4 ตัว) กับตำแหน่งดัชนีที่พยายามเข้าถึง (ดัชนี 4)
- ทั้งสามตัวอย่างของหัวข้อนี้มีโครงสร้างเดียวกันทุกประการ ต่างกันเพียงชนิดข้อผิดพลาดและโดเมน แสดงว่ารูปแบบพื้นฐานนี้ประยุกต์ใช้ได้หลากหลาย (หากเปลี่ยนดัชนีจาก 4 เป็น 3 บล็อก `try` จะทำงานสำเร็จทั้งหมด)

## Slide 13 — Exception Types ที่พบบ่อย
**Key Message**: 4 ชนิดข้อผิดพลาดพบบ่อยที่สุดในโปรแกรมระดับเบื้องต้น แต่ละชนิดมีสาเหตุเฉพาะของตนเอง

- ข้อผิดพลาดขณะรันไม่ได้มีเพียงชนิดเดียว การรู้จักชื่อและสาเหตุของข้อผิดพลาดแต่ละชนิดเป็นพื้นฐานสำคัญก่อนเขียนโค้ดดักจับให้ถูกต้อง

| ชนิดข้อผิดพลาด | เกิดขึ้นเมื่อใด |
|---|---|
| `ZeroDivisionError` | หารด้วยศูนย์ |
| `ValueError` | แปลงชนิดข้อมูลด้วยค่าที่แปลงไม่ได้ |
| `TypeError` | ดำเนินการระหว่างชนิดข้อมูลที่ไม่สอดคล้องกัน |
| `IndexError` | เข้าถึงดัชนีที่ไม่มีอยู่จริง |

- ทั้ง 4 ชนิดนี้เป็นเพียงส่วนหนึ่งของชนิดมาตรฐานทั้งหมดในไพทอน แต่พบบ่อยที่สุดในโปรแกรมระดับเบื้องต้น

---

## Slide 14 — ตัวอย่าง 3.1: ระบบตัดเกรดนักเรียน (ครบทั้ง 4 ชนิดในโปรแกรมเดียว)
**Key Message**: แม้อยู่ในบริบทเดียวกัน สาเหตุการเกิดข้อผิดพลาดแต่ละชนิดแตกต่างกันโดยสิ้นเชิง

```python
print("สาธิตข้อผิดพลาดที่พบบ่อยในระบบตัดเกรดนักเรียน")

scores = []
try:
    average = sum(scores) / len(scores)
    print("ค่าเฉลี่ยคือ", average)
except ZeroDivisionError:
    print("ZeroDivisionError: ไม่มีคะแนนให้คำนวณค่าเฉลี่ย")

grade_text = "A+"
try:
    grade_number = int(grade_text)
    print("เกรดตัวเลขคือ", grade_number)
except ValueError:
    print("ValueError: ไม่สามารถแปลงตัวอักษรเกรดเป็นตัวเลขได้")

bonus_score = "5"
base_score = 70
try:
    final_score = base_score + bonus_score
    print("คะแนนรวมคือ", final_score)
except TypeError:
    print("TypeError: ไม่สามารถบวกตัวเลขกับข้อความได้โดยตรง")

student_grades = [85, 90, 78]
try:
    fourth_grade = student_grades[3]
    print("เกรดคนที่สี่คือ", fourth_grade)
except IndexError:
    print("IndexError: ไม่มีนักเรียนลำดับนี้ในรายชื่อ")
```

**Output:**
```
สาธิตข้อผิดพลาดที่พบบ่อยในระบบตัดเกรดนักเรียน
ZeroDivisionError: ไม่มีคะแนนให้คำนวณค่าเฉลี่ย
ValueError: ไม่สามารถแปลงตัวอักษรเกรดเป็นตัวเลขได้
TypeError: ไม่สามารถบวกตัวเลขกับข้อความได้โดยตรง
IndexError: ไม่มีนักเรียนลำดับนี้ในรายชื่อ
```

- แม้อยู่ในบริบทเดียวกัน สาเหตุการเกิดข้อผิดพลาดแตกต่างกันโดยสิ้นเชิง การรู้จักชื่อและสาเหตุเฉพาะช่วยวินิจฉัยปัญหาได้เร็วขึ้น

## Slide 17 — สรุป: ValueError vs TypeError
**Key Message**: ValueError คือ "ชนิดถูกแต่ค่าไม่เหมาะ" ส่วน TypeError คือ "ชนิดไม่รองรับการดำเนินการนั้นเลย"

| ชนิดข้อผิดพลาด | ชนิดข้อมูลตั้งต้น | สาเหตุ |
|---|---|---|
| `ValueError` | ถูกต้องตามที่ฟังก์ชันต้องการ (เช่น `str` ที่จะแปลงเป็น `int`) | ค่าภายในไม่สามารถแปลงได้ตามชนิดที่ต้องการ |
| `TypeError` | ไม่สอดคล้องกัน (เช่น `int` กับ `str`) | ตัวดำเนินการนั้นไม่รองรับชนิดข้อมูลที่นำมาปะปนกันเลย |

- ลำดับการเรียงในตารางสรุปของหัวข้อนี้ (`ZeroDivisionError`, `ValueError`, `TypeError`, แล้วจึง `IndexError`) ปรากฏซ้ำเหมือนกันในทุกตัวอย่างของหัวข้อนี้

## Slide 18 — จับหลาย exception ในฟังก์ชันเดียว
**Key Message**: หนึ่งฟังก์ชันหลายขั้นตอน ควรมีทางรับมือแยกกันตามชนิดข้อผิดพลาดที่อาจเกิด

- เมื่อฟังก์ชันมีหลายขั้นตอนที่แต่ละขั้นตอนอาจก่อข้อผิดพลาดคนละชนิด แนวคิดทั่วไปคือเตรียมทางรับมือแยกกันสำหรับแต่ละชนิด เพื่อตอบสนองต่อสาเหตุของปัญหาได้อย่างเจาะจง
- ในไพทอน เขียนบล็อก `except` มากกว่าหนึ่งบล็อกต่อจาก `try` เดียวกัน แต่ละบล็อกระบุชนิดของตนเอง
- ไพทอนตรวจสอบบล็อก `except` ตามลำดับจากบนลงล่าง เลือกบล็อกแรกที่ชนิดตรงกัน
- หากไม่มีบล็อกใดตรงกันเลย ข้อผิดพลาดจะแพร่กระจายออกไปนอกฟังก์ชันเหมือนไม่มีการดักจับใด ๆ

**Key Message**: ลำดับบล็อก except มีผลเฉพาะเมื่อชนิดข้อผิดพลาดซ้อนทับกัน (เนื้อหาขั้นสูงกว่าสัปดาห์นี้)

- ในทั้ง 3 ตัวอย่างของหัวข้อนี้ ลำดับของบล็อก `except` ไม่มีผลต่อผลลัพธ์ เพราะ `ZeroDivisionError`, `ValueError` และ `IndexError` ไม่ทับซ้อนกัน แต่ละชนิดถูกเลือกโดยชนิดที่ตรงกันเท่านั้น
- ฟังก์ชันทุกฟังก์ชันในหัวข้อนี้ return ค่าเดียวเสมอในทุกเส้นทางการทำงาน ทั้งกรณีสำเร็จและกรณีเกิดข้อผิดพลาดแต่ละชนิด สอดคล้องกับรูปแบบฟังก์ชันที่สืบทอดมาจากสัปดาห์ที่ 6

## Slide 23 — Defensive Function: เขียนฟังก์ชันให้ทนทานต่อ error
**Key Message**: ฟังก์ชันเชิงป้องกันคืนค่าเดียวเสมอ ไม่ปล่อยให้ข้อผิดพลาดแพร่กระจายออกไป

- การเขียนโปรแกรมเชิงป้องกัน (defensive programming) คือออกแบบฟังก์ชันให้รับมือกับข้อมูลนำเข้าที่ไม่ถูกต้องได้ โดยไม่ทำให้โปรแกรมทั้งระบบหยุดทำงาน
- ในบริบทของสัปดาห์นี้หมายถึงการนำ `try`/`except` มาห่อหุ้มการดำเนินการที่อาจก่อข้อผิดพลาดไว้ภายในฟังก์ชัน
- เป้าหมายคือให้ฟังก์ชันนั้น "ปลอดภัย" เสมอ — คืนค่าออกมาเป็นค่าเดียวเสมอ สอดคล้องโดยตรงกับฟังก์ชัน `safe_divide` (Slide 5 ของสไลด์เดิม)
- ฟังก์ชันลักษณะนี้มักตั้งชื่อขึ้นต้นด้วย `safe_`

## Slide 24 — ตัวอย่าง 5.1: safe_get_average
**Key Message**: return ค่าเดียวเสมอในทุกกรณี — คุณสมบัติสำคัญของฟังก์ชันเชิงป้องกัน

```python
def safe_get_average(scores):
    try:
        return sum(scores) / len(scores)
    except ZeroDivisionError:
        return 0

print(safe_get_average([]))
```

```

0
```

- return ค่าเดียวเสมอในทุกกรณี (ทั้ง `80.0` และ `0`) เป็นคุณสมบัติสำคัญของฟังก์ชันเชิงป้องกันตามรูปแบบที่สืบทอดจาก `safe_divide`
- ดักจับเฉพาะ `ZeroDivisionError` เท่านั้น ความปลอดภัยของฟังก์ชันนี้จึงจำกัดเฉพาะกรณีนั้น

## Slide 29 — ส่วน else: ทำงานเฉพาะเมื่อไม่มีข้อผิดพลาด
**Key Message**: `else` แนบท้าย try/except คือโค้ดที่ควรทำงาน "เฉพาะเมื่อ try สำเร็จ" เท่านั้น

- หลายภาษาไม่มีกลไกนี้โดยตรง ต้องใช้ตัวแปรสถานะ (flag) หรือวางโค้ดต่อท้ายทั้งโครงสร้างแทน
- Python มี `else` แนบท้าย try/except โดยเฉพาะสำหรับจุดประสงค์นี้
- ลำดับการทำงาน: `else` ทำงานหลัง try จบสมบูรณ์โดยไม่มีข้อผิดพลาด และทำงานก่อน `finally` (ถ้ามี)
- ตัวแปรที่สร้างใน try ยังใช้ได้ปกติใน else เพราะอยู่ scope เดียวกัน
- ประโยชน์เชิงออกแบบ: แยก "โค้ดเสี่ยง" (ไว้ใน try) ออกจาก "โค้ดที่ควรทำงานเฉพาะเมื่อสำเร็จ" (ไว้ใน else)

## Slide 30 — ตัวอย่าง: ตรวจสอบคะแนนสอบด้วย try/except/else
**Key Message**: else ทำงานเมื่อแปลงค่าสำเร็จ except ทำงานเมื่อแปลงค่าไม่สำเร็จ — ทำงานแยกกันเสมอ

```python
def read_score(text):
    try:
        score = int(text)
    except ValueError:
        print("แปลงคะแนนไม่สำเร็จ:", text)
    else:
        print("แปลงคะแนนสำเร็จ:", score)

read_score("85")
read_score("แปดสิบ")
```

**Output:**
```
แปลงคะแนนสำเร็จ: 85
แปลงคะแนนไม่สำเร็จ: แปดสิบ
```

- ตัวแปร `score` ที่สร้างในบล็อก try ใช้งานได้ปกติในส่วน else เพราะอยู่ scope เดียวกัน
- หากย้าย `print(...)` จาก else เข้าไปต่อท้ายใน try แทน ผลลัพธ์จะเหมือนเดิมทุกประการในกรณีนี้ — ความต่างจะปรากฏชัดเมื่อโค้ดที่ย้ายมามีโอกาสก่อข้อผิดพลาดเอง

## Slide 31 — ตัวอย่าง: ค้นหาเงินเดือนพนักงาน (KeyError)
**Key Message**: else ใช้ได้กับข้อผิดพลาดชนิดใดก็ได้ ไม่จำกัดเฉพาะ ValueError

```python
salary_table = {"E001": 25000, "E002": 30000}

def show_salary(emp_id):
    try:
        salary = salary_table[emp_id]
    except KeyError:
        print("ไม่พบรหัสพนักงาน:", emp_id)
    else:
        print("เงินเดือนของ", emp_id, "คือ", salary)

show_salary("E001")
show_salary("E999")
```

**Output:**
```
เงินเดือนของ E001 คือ 25000
ไม่พบรหัสพนักงาน: E999
```

- `KeyError` เกิดจากการเข้าถึง dict ด้วยคีย์ที่ไม่มีอยู่จริง เทียบเคียงได้กับ `IndexError` ของ list แต่เป็นโครงสร้างข้อมูลคนละชนิด
- โค้ดเสี่ยง (การเข้าถึง dict) อยู่ใน try ส่วนการแสดงผลที่ปลอดภัยแล้วแยกไปไว้ใน else — รูปแบบเดียวกับตัวอย่างก่อนหน้า คนละโดเมนข้อมูล

## Slide 32 — Edge Case: ข้อผิดพลาดที่เกิดขึ้นภายใน else เอง
**Key Message**: except ที่เขียนคู่กันดักจับข้อผิดพลาดที่เกิดใน else ไม่ได้ แม้ชนิดจะตรงกันทุกประการ

```python
def convert_temperature(text):
    try:
        celsius = float(text)
    except ValueError:
        print("แปลงอุณหภูมิไม่สำเร็จ:", text)
    else:
        if celsius < -273.15:
            raise ValueError("อุณหภูมิต่ำกว่าศูนย์องศาสัมบูรณ์")
        fahrenheit = celsius * 9 / 5 + 32
        print("องศาฟาเรนไฮต์:", fahrenheit)

convert_temperature("100")
convert_temperature("-300")
```

**Output:**
```
องศาฟาเรนไฮต์: 212.0
Traceback (most recent call last):
  ...
ValueError: อุณหภูมิต่ำกว่าศูนย์องศาสัมบูรณ์
```

- `"-300"` เป็นรูปแบบตัวเลขที่ถูกต้อง จึงแปลงสำเร็จในบล็อก try และเข้าสู่ else — แต่เงื่อนไขทางฟิสิกส์ในบรรทัด else พบว่าค่านี้ไม่ถูกต้อง จึง `raise` ขึ้นเอง
- แม้ข้อผิดพลาดใหม่นี้เป็น `ValueError` ตรงกับที่ `except ValueError` ดักไว้ทุกประการ except นั้นก็ยังดักจับไม่ได้ เพราะขอบเขตการดักจับครอบคลุมเฉพาะบล็อก try เท่านั้น
- หากต้องการดักจับข้อผิดพลาดที่อาจเกิดใน else ด้วย ต้องเขียน try/except ซ้อนอีกชุด (nested try/except)

## Slide 34 — สรุปหัวข้อ 6: except ไม่คุ้มครอง else
**Key Message**: except คุ้มครองเฉพาะสิ่งที่เกิดขึ้นในบล็อก try เท่านั้น ไม่ขยายไปคุ้มครอง else แม้ชนิดจะตรงกัน

- else ทำงานเฉพาะเมื่อบล็อก try ทั้งหมดจบลงโดยไม่มีข้อผิดพลาดเลยเท่านั้น
- ข้อผิดพลาดที่เกิดขึ้นภายใน else จะไม่ถูกดักจับโดย except ที่เขียนคู่กันเลย ไม่ว่าชนิดจะตรงกันหรือไม่ก็ตาม
- การแยกโค้ดเสี่ยง (try) ออกจากโค้ดที่ควรทำงานเฉพาะเมื่อสำเร็จ (else) ช่วยให้อ่านโค้ดแล้วแยกแยะขอบเขตความเสี่ยงได้ทันที

---

## Slide 35 — ส่วน finally: รันเสมอไม่มีเงื่อนไข
**Key Message**: finally ทำงานเสมอ ไม่ว่า try จะสำเร็จ เกิดข้อผิดพลาดที่ดักได้ หรือไม่มีใครดักได้เลยก็ตาม

- ใช้สำหรับงาน cleanup: ปิดการเชื่อมต่ออุปกรณ์, คืนทรัพยากรที่ยืมมา, บันทึกว่าขั้นตอนตรวจสอบเสร็จสิ้น
- ลำดับการทำงาน: `finally` ทำงานหลังจาก try (และ except หรือ else) ประมวลผลเสร็จสิ้นแล้วในทุกกรณี
- แม้มี `return` ใน try หรือ except ค่าที่จะส่งกลับจะถูกรอไว้จนกว่า finally จะทำงานเสร็จแล้วจึงส่งกลับจริง
- `finally` ไม่ได้ทำหน้าที่ดักจับหรือระงับข้อผิดพลาดด้วยตัวเอง — ถ้า try เกิดข้อผิดพลาดที่ไม่มี except ดักจับ ข้อผิดพลาดจะยังคงแพร่กระจายต่อหลังจาก finally ทำงานเสร็จ
- ต่างจาก else ตรงเงื่อนไข: else ทำงานเฉพาะกรณีสำเร็จ finally ทำงานเสมอไม่มีเงื่อนไข

## Slide 36 — ตัวอย่าง: คำนวณค่าเฉลี่ยคะแนนสองวิชา

```python
def average_of_two(a, b):

    except TypeError:

    finally:
        print("ประมวลผลคะแนนคู่นี้เสร็จสิ้น")

average_of_two(80, 90)
average_of_two(80, "เก้าสิบ")
```

- ข้อความ "ประมวลผลคะแนนคู่นี้เสร็จสิ้น" ปรากฏทั้งสองครั้งของการเรียก ไม่ว่าจะสำเร็จหรือเกิดข้อผิดพลาด — คุณสมบัติเฉพาะที่ else ไม่มี
- ลำดับการทำงานคงที่เสมอ: try/except ทำงานก่อน แล้ว finally ทำงานทีหลังเสมอ

## Slide 38 — Edge Case: finally ทำงานก่อนค่า return ถูกส่งออกจริง
**Key Message**: แม้มี return ใน try ฟังก์ชันก็ยังไม่ออกทันที — finally แทรกทำงานก่อนเสมอ

```python
def is_password_valid(password):
    try:
        if len(password) < 8:
            return False
        return True
    finally:
        print("ตรวจสอบความยาวรหัสผ่านเสร็จสิ้น")

print("ผลตรวจสอบ 1:", is_password_valid("abc"))
print("ผลตรวจสอบ 2:", is_password_valid("abcdefgh"))
```

**Output:**
```
ตรวจสอบความยาวรหัสผ่านเสร็จสิ้น
ผลตรวจสอบ 1: False
ตรวจสอบความยาวรหัสผ่านเสร็จสิ้น
ผลตรวจสอบ 2: True
```

- ข้อความจาก finally ปรากฏก่อนข้อความที่แสดงค่าที่ return เสมอในทุกบรรทัดของผลลัพธ์ ยืนยันว่า finally ทำงานก่อนค่าจะถูกส่งกลับออกไปจริง
- ฟังก์ชันนี้ยัง return ค่าเดียวเสมอในทุกเส้นทาง (มีเพียง True หรือ False) แม้จะมีจุดออกจากฟังก์ชันสองจุด

---

## Slide 39 — สรุปหัวข้อ 7: finally รันก่อน return จะเสร็จสมบูรณ์จริง
**Key Message**: return ใน try ไม่ได้ทำให้ฟังก์ชันออกทันที — ค่าที่จะคืนถูกรอไว้จนกว่า finally จะทำงานเสร็จก่อนเสมอ

- ลำดับการทำงานคงที่ตายตัว: try (หรือ except/else ถ้าเข้าสู่ส่วนใดส่วนหนึ่ง) ทำงานก่อน แล้ว finally ทำงานทีหลังเสมอ ไม่มีทางสลับลำดับได้
- finally ไม่ได้ทำให้ข้อผิดพลาดหายไป — ถ้าไม่มี except ดักจับ finally ยังคงทำงานก่อน แล้วข้อผิดพลาดจึงแพร่กระจายต่อหลังจากนั้น
- ต่างจาก else ที่ทำงานเฉพาะกรณีสำเร็จเท่านั้น finally คือกลไกเดียวที่รับประกันว่าจะทำงานในทุกเส้นทางไม่มีข้อยกเว้น

## Slide 40 — except ... as e: เข้าถึงอ็อบเจกต์ข้อผิดพลาดจริง
**Key Message**: `except ExceptionType as e` ผูกอ็อบเจกต์ข้อผิดพลาดจริงเข้ากับตัวแปร ไม่ใช่แค่จับชนิดไว้เฉย ๆ

- เมื่อเกิดข้อผิดพลาด Python สร้างอ็อบเจกต์ที่บรรจุรายละเอียดของข้อผิดพลาดนั้นไว้ด้วย ไม่ใช่แค่ระบุชนิด
- เมื่อพิมพ์ตัวแปรนี้ผ่าน `print()` โดยตรง Python เรียก `str(e)` ให้อัตโนมัติ
- ข้อความจริงที่ Python สร้างเองมีรายละเอียดเชิงเทคนิคมากกว่าข้อความที่ผู้เขียนโปรแกรมกำหนดเอง เหมาะกับการบันทึก debug
- ตัวแปร `e` มีขอบเขตจำกัดอยู่เฉพาะภายในบล็อก except เท่านั้น เมื่อออกจากบล็อกจะถูกลบทิ้งอัตโนมัติ
- `e.args` คือ tuple ของอาร์กิวเมนต์ที่ใช้สร้างอ็อบเจกต์ข้อผิดพลาด, `type(e).__name__` คืนชื่อชนิดเป็นข้อความ

## Slide 41 — ตัวอย่าง: หารจำนวนแล้วแสดงข้อความข้อผิดพลาดจริง
**Key Message**: "division by zero" ไม่ได้เขียนโดยผู้เขียนโปรแกรมเลย เป็นข้อความที่ Python สร้างขึ้นเอง

```python
def divide(a, b):
    try:
        result = a / b
        print("ผลหาร:", result)
    except ZeroDivisionError as e:
        print("เกิดข้อผิดพลาด:", e)

divide(10, 2)
divide(10, 0)
```

**Output:**
```
ผลหาร: 5.0
เกิดข้อผิดพลาด: division by zero
```

- `print("เกิดข้อผิดพลาด:", e)` พิมพ์ `e` ได้โดยตรง เพราะ Python เรียก `str(e)` ให้อัตโนมัติ
- ตัวแปร `e` ถูกลบทิ้งอัตโนมัติเมื่อออกจากบล็อก except — การพิมพ์ `e` นอกบล็อกจะเกิด `NameError`

## Slide 42 — ตัวอย่าง: ลงทะเบียนอายุผู้ใช้งาน

```python
def register_age(text):

register_age("25")
```

## Slide 43 — Edge Case: รูปแบบข้อความต่างกันตามชนิดข้อผิดพลาด
**Key Message**: str(e) ไม่มีรูปแบบตายตัวเหมือนกันในทุกชนิด — KeyError ให้เพียง repr ของคีย์ที่ไม่พบ

```python
inventory = {"apple": 10, "banana": 5}

def check_stock(item):
    try:
        quantity = inventory[item]
        print("จำนวนคงเหลือ:", quantity)
    except KeyError as e:
        print("ชนิดข้อผิดพลาด:", type(e).__name__)
        print("ข้อความจาก str(e):", str(e))
        print("ข้อความจาก e.args:", e.args)

check_stock("apple")
check_stock("mango")
```

**Output:**
```
จำนวนคงเหลือ: 10
ชนิดข้อผิดพลาด: KeyError
ข้อความจาก str(e): 'mango'
ข้อความจาก e.args: ('mango',)
```

- `str(e)` ของ `KeyError` แสดงเป็น `'mango'` (มีเครื่องหมายคำพูด) ไม่ใช่ประโยคอธิบายแบบ `ZeroDivisionError`/`ValueError` ในสไลด์ก่อนหน้า
- `e.args` คือ tuple ของอาร์กิวเมนต์ดิบที่ใช้สร้างอ็อบเจกต์ข้อผิดพลาด — `str(e)` คือการแปลง args เหล่านี้เป็นข้อความตามรูปแบบเฉพาะของแต่ละชนิด

## Slide 44 — สรุปหัวข้อ 8: e มีขอบเขตจำกัดและรูปแบบไม่ตายตัว
**Key Message**: ข้อความจริงจาก except...as e ให้รายละเอียดเชิงเทคนิคที่มีประโยชน์ แต่ไม่มีรูปแบบเดียวกันตายตัวในทุกชนิด

- ตัวแปร `e` มีขอบเขตจำกัดอยู่เฉพาะภายในบล็อก except เท่านั้น ใช้ต่อภายนอกบล็อกไม่ได้
- รูปแบบข้อความจาก `str(e)` แตกต่างกันไปตามชนิดข้อผิดพลาด: บางชนิดให้ประโยคอธิบายเต็มรูปแบบ บางชนิดให้เพียงค่าที่เกี่ยวข้อง
- ผู้เขียนโปรแกรมไม่ควรคาดหวังรูปแบบข้อความที่ตายตัวเมื่อออกแบบระบบที่ต้องแยกวิเคราะห์ข้อความเหล่านี้ต่อ

## Slide 45 — raise: การโยนข้อผิดพลาดเองด้วยเงื่อนไขทางธุรกิจ
**Key Message**: `raise` ให้ผู้เขียนโปรแกรมกำหนดเงื่อนไขตรวจสอบเฉพาะของระบบเองได้ ไม่ต้องรอให้ Python สร้างข้อผิดพลาดให้

- นอกจากข้อผิดพลาดที่เกิดขึ้นเองตามธรรมชาติ ผู้เขียนโปรแกรมยังกำหนดเงื่อนไขตรวจสอบ (validation) เฉพาะของระบบเองได้ เช่น อายุต้องไม่ติดลบ
- รูปแบบการเขียน: `raise ExceptionType("ข้อความ")`
- หากไม่มี except ใดดักจับได้ ข้อผิดพลาดจะแพร่กระจายจนถึงจุดเริ่มต้นของโปรแกรม ทำให้หยุดทำงานพร้อม traceback เหมือนข้อผิดพลาดตามธรรมชาติ
- `raise` ใช้กลไกการดักจับและแพร่กระจายเดียวกันกับ try/except ทั้งหมด ไม่ใช่กลไกที่แยกต่างหาก
- เมื่อ raise ทำงาน คำสั่งถัดไปในฟังก์ชันเดียวกันจะไม่ถูกประมวลผลเลย

## Slide 46 — ตัวอย่าง: ตรวจสอบอายุก่อนลงทะเบียนผู้ใช้งาน
**Key Message**: ข้อผิดพลาดจาก raise ถูกดักจับด้วย try/except เดียวกันทุกประการกับข้อผิดพลาดตามธรรมชาติ

```python
def register_user(age):
    if age < 0:
        raise ValueError("อายุต้องไม่ติดลบ")
    print("ลงทะเบียนสำเร็จ อายุ:", age)

register_user(20)
try:
    register_user(-5)
except ValueError as e:
    print("ลงทะเบียนไม่สำเร็จ:", e)
```

**Output:**
```
ลงทะเบียนสำเร็จ อายุ: 20
ลงทะเบียนไม่สำเร็จ: อายุต้องไม่ติดลบ
```

- ข้อความ "อายุต้องไม่ติดลบ" เป็นข้อความที่ผู้เขียนโปรแกรมกำหนดขึ้นเองทั้งหมด ต่างจากหัวข้อ 8 ที่ข้อความมาจาก Python โดยตรง
- เมื่อ `raise` ทำงาน คำสั่ง `print("ลงทะเบียนสำเร็จ...")` ที่อยู่ถัดไปจะไม่ถูกประมวลผลเลย

## Slide 47 — ตัวอย่าง: ตรวจสอบสินค้าคงเหลือก่อนสั่งซื้อ
**Key Message**: raise ผสานกับ defensive programming ในฟังก์ชันเดียวกันได้

```python
stock = {"เสื้อยืด": 3}

def place_order(item, quantity):
    if quantity > stock.get(item, 0):
        raise ValueError("สินค้าในคลังไม่พอสำหรับคำสั่งซื้อนี้")
    print("สั่งซื้อสำเร็จ:", item, "จำนวน", quantity)

place_order("เสื้อยืด", 2)
try:
    place_order("เสื้อยืด", 10)
except ValueError as e:
    print("สั่งซื้อไม่สำเร็จ:", e)
```

**Output:**
```
สั่งซื้อสำเร็จ: เสื้อยืด จำนวน 2
สั่งซื้อไม่สำเร็จ: สินค้าในคลังไม่พอสำหรับคำสั่งซื้อนี้
```

- `stock.get(item, 0)` ป้องกัน `KeyError` เมื่อสินค้านั้นไม่มีอยู่ในคลังเลย (คืนค่า 0 แทน) แสดงว่า defensive programming และ `raise` ใช้ร่วมกันในฟังก์ชันเดียวกันได้
- เงื่อนไข validation นี้เป็นกฎทางธุรกิจเฉพาะของระบบนี้เท่านั้น ไม่มีทางที่ Python จะรู้ล่วงหน้าหรือสร้างข้อผิดพลาดให้เองโดยอัตโนมัติ

## Slide 48 — Edge Case: raise ที่ไม่มีการดักจับ เทียบกับที่มีการดักจับ
**Key Message**: raise เพียงอย่างเดียวไม่ได้ทำให้โปรแกรมปลอดภัยขึ้นโดยอัตโนมัติ ยังต้องจับคู่กับ try/except

```python
def validate_temperature(celsius):
    if celsius < -273.15:
        raise ValueError("อุณหภูมิต่ำกว่าศูนย์องศาสัมบูรณ์")
    print("อุณหภูมิถูกต้อง:", celsius)

validate_temperature(25)
validate_temperature(-300)
print("บรรทัดนี้จะไม่ถูกประมวลผล")
```

**Output (ไม่มี try/except ครอบ):**
```
อุณหภูมิถูกต้อง: 25
Traceback (most recent call last):
  ...
ValueError: อุณหภูมิต่ำกว่าศูนย์องศาสัมบูรณ์
```

เปรียบเทียบกับโค้ดเดียวกันที่ครอบด้วย try/except:

```python
validate_temperature(25)
try:
    validate_temperature(-300)
except ValueError as e:
    print("ตรวจพบค่าที่ไม่ถูกต้อง:", e)
print("โปรแกรมทำงานต่อได้ตามปกติ")
```

**Output (มี try/except ครอบ):**
```
อุณหภูมิถูกต้อง: 25
ตรวจพบค่าที่ไม่ถูกต้อง: อุณหภูมิต่ำกว่าศูนย์องศาสัมบูรณ์
โปรแกรมทำงานต่อได้ตามปกติ
```

- ข้อผิดพลาดจาก raise ที่ไม่มีการดักจับมีพฤติกรรมเหมือนข้อผิดพลาดตามธรรมชาติที่ไม่มีการดักจับทุกประการ — คำสั่งถัดจากจุดเกิดข้อผิดพลาดไม่ถูกประมวลผลเลย
- เมื่อครอบด้วย try/except โปรแกรมทำงานต่อไปได้จนถึงบรรทัดสุดท้าย ยืนยันว่า raise กับ try/except เป็นกลไกที่ต้องใช้คู่กันเสมอ

## Slide 49 — สรุปหัวข้อ 9: raise ต้องจับคู่กับ try/except เสมอ
**Key Message**: raise ทำหน้าที่แจ้งปัญหา ส่วน try/except ทำหน้าที่รับมือกับปัญหานั้นเพื่อให้โปรแกรมทำงานต่อได้

- `raise` ใช้กลไกการดักจับและแพร่กระจายเดียวกันทุกประการกับข้อผิดพลาดตามธรรมชาติ ไม่มีวากยสัมพันธ์พิเศษเพิ่มเติม
- ข้อความจาก `raise` เป็นข้อความที่ผู้เขียนโปรแกรมกำหนดเอง ต่างจากข้อความจริงของ Python ในหัวข้อ 8

## Slide 51 — Custom Exception คืออะไร
**Key Message**: สร้างคลาสข้อผิดพลาดของตัวเองได้ ด้วยการสืบทอดจาก `Exception`

- ข้อผิดพลาดมาตรฐานของภาษาไม่สื่อความหมายเฉพาะเจาะจงกับปัญหาในโดเมนของโปรแกรมเสมอไป
- สร้างคลาสใหม่สืบทอดจาก `Exception` (หรือคลาสย่อยของ `Exception`) เพื่อให้ยังทำงานร่วมกับ `try`/`except`/`raise` ได้ตามปกติทุกประการ
- อาจเพิ่ม `__init__` ของตนเองเพื่อเก็บข้อมูลเฉพาะ หรือใช้เพียง `pass` ก็ได้
- ต่อยอดจากหัวข้อ 9 (`raise`) และหัวข้อ 8 (`except X as e`)

## Slide 52 — ตัวอย่าง: Custom Exception ขั้นต่ำสุด
**Key Message**: แค่ `class ... (Exception): pass` ก็ใช้งานได้ครบเหมือน exception มาตรฐาน

```python
class InvalidGradeError(Exception):
    pass

def check_grade(score):
    if score < 0 or score > 100:
        raise InvalidGradeError("คะแนนต้องอยู่ระหว่าง 0 ถึง 100")
    return score

try:
    check_grade(120)
except InvalidGradeError as e:
    print("พบข้อผิดพลาด:", e)

print(check_grade(85))
```

**Output:**
```
พบข้อผิดพลาด: คะแนนต้องอยู่ระหว่าง 0 ถึง 100
85
```

- แม้ไม่มี `__init__` ของตัวเองเลย ยังส่งข้อความเข้าไปตอนสร้างอ็อบเจกต์และให้ `print(e)` แสดงถูกต้องได้ เพราะ `Exception` มี `__init__`/`__str__` มาตรฐานรองรับอยู่แล้ว
- `except InvalidGradeError as e` ทำงานเหมือนกับการดักข้อผิดพลาดมาตรฐานทุกประการ

## Slide 53 — ตัวอย่าง: Custom Exception พร้อมข้อมูลประกอบ
**Key Message**: custom exception พกข้อมูลโครงสร้าง (structured data) ติดตัวไปได้ ไม่ใช่แค่ข้อความ

```python
class BookNotAvailableError(Exception):
    def __init__(self, title, remaining):
        self.title = title
        self.remaining = remaining
        self.message = f"หนังสือ '{title}' ไม่พร้อมให้ยืม (คงเหลือ {remaining} เล่ม)"
        super().__init__(self.message)

    def __str__(self):
        return self.message

library_stock = {"Python เบื้องต้น": 0, "โครงสร้างข้อมูล": 3}

def borrow_book(title):
    remaining = library_stock.get(title, 0)
    if remaining <= 0:
        raise BookNotAvailableError(title, remaining)
    library_stock[title] = remaining - 1
    return f"ยืม '{title}' สำเร็จ คงเหลือ {library_stock[title]} เล่ม"

try:
    print(borrow_book("Python เบื้องต้น"))
except BookNotAvailableError as e:
    print("ยืมไม่สำเร็จ:", e)
    print("ชื่อหนังสือที่พบปัญหา:", e.title)

print(borrow_book("โครงสร้างข้อมูล"))
```

**Output:**
```
ยืมไม่สำเร็จ: หนังสือ 'Python เบื้องต้น' ไม่พร้อมให้ยืม (คงเหลือ 0 เล่ม)
ชื่อหนังสือที่พบปัญหา: Python เบื้องต้น
ยืม 'โครงสร้างข้อมูล' สำเร็จ คงเหลือ 2 เล่ม
```

- `e.title` เข้าถึงได้ทันทีโดยไม่ต้องแกะจากข้อความ `str(e)` เลย — เป็นประโยชน์หลักของการเขียน `__init__` ของตนเอง
- `super().__init__(self.message)` ทำให้ `str(e)` และกลไกมาตรฐานของ exception ทำงานถูกต้องครบ

## Slide 54 — ตัวอย่าง: ไม่เรียก `super().__init__()`
**Key Message**: `str(e)` และ `e.args` ยังทำงานได้แม้ลืมเรียก `super().__init__()`

```python
class InsufficientFundsError(Exception):
    def __init__(self, balance, amount):
        self.balance = balance
        self.amount = amount
        # ไม่ได้เรียก super().__init__() ส่งข้อความใด ๆ ให้คลาสฐาน

def withdraw(balance, amount):
    if amount > balance:
        raise InsufficientFundsError(balance, amount)
    return balance - amount

try:
    withdraw(500, 800)
except InsufficientFundsError as e:
    print("str(e) แสดงผลว่า:", repr(str(e)))
    print("แต่ยังเข้าถึง e.balance ได้:", e.balance)
    print("และเข้าถึง e.amount ได้:", e.amount)
    print("e.args ที่คลาสฐานเก็บไว้:", e.args)
```

**Output:**
```
str(e) แสดงผลว่า: '(500, 800)'
แต่ยังเข้าถึง e.balance ได้: 500
และเข้าถึง e.amount ได้: 800
e.args ที่คลาสฐานเก็บไว้: (500, 800)
```

- `BaseException.__new__` ตั้งค่า `e.args` ก่อน `__init__` ของคลาสลูกเสมอ ไม่ขึ้นกับว่า `__init__` จะเรียก `super().__init__()` หรือไม่
- `str(e)` แบบมาตรฐานของ `BaseException` แสดงผลจาก `self.args` เป็น tuple เมื่อมีมากกว่า 1 ค่า

## Slide 55 — สรุป: `__new__` มาก่อน `__init__` เสมอ
**Key Message**: `args` ถูกกำหนดที่ `BaseException.__new__` ไม่ใช่ที่ `__init__` ของคลาสลูก

| สถานการณ์ | เรียก `super().__init__()` | `e.args` มีค่าหรือไม่ |
|---|---|---|
| ตัวอย่าง 10.3 (`BookNotAvailableError`) | เรียก | มีค่า (ผ่าน `message`) |
| ตัวอย่าง 10.4 (`InsufficientFundsError`) | ไม่เรียก | ยังมีค่า (ผ่าน `__new__` ของ `BaseException`) |

- คลาสลูกที่เขียน `__init__` ทับคลาสฐานโดยไม่เรียก `super().__init__()` ปกติแล้วแอตทริบิวต์ที่คลาสฐานตั้งค่าให้จะไม่ถูกตั้งค่า แต่ `BaseException` ทำงานต่างออกไปตรงที่ `args` มาจาก `__new__` ซึ่งทำงานก่อน `__init__` เสมอ
- ผลคือ `str(e)` ยังทำงานได้แม้ผู้เขียนคลาสลืมเรียก `super().__init__()`

## Slide 56 — ลำดับชั้นของข้อผิดพลาด (Exception Hierarchy)
**Key Message**: exception จัดเรียงเป็นต้นไม้ — ดักที่คลาสแม่ ดักได้ทั้งคลาสลูก

- ข้อผิดพลาดชนิดที่เจาะจงกว่าสืบทอดคุณสมบัติมาจากชนิดที่กว้างกว่า
- ทั้งหมดสืบทอดจาก `BaseException`; ถัดลงมาคือ `Exception`
- `SystemExit`/`KeyboardInterrupt` สืบทอดจาก `BaseException` โดยตรง ไม่ใช่ลูกของ `Exception`

## Slide 59 — ตัวอย่าง: ดักข้อผิดพลาดกลุ่มเดียวกันด้วยคลาสแม่
**Key Message**: `except ArithmeticError` บล็อกเดียวดักได้ทั้ง `ZeroDivisionError` และ `OverflowError`

```python
import math

def calculate(op, a, b):
    try:
        if op == "divide":
            return a / b
        elif op == "power":
            return math.exp(a ** b)
    except ArithmeticError as e:
        return f"คำนวณไม่ได้ ({type(e).__name__}): {e}"

print(calculate("divide", 10, 0))
print(calculate("power", 10, 5000))
print(calculate("divide", 10, 2))
```

**Output:**
```
คำนวณไม่ได้ (ZeroDivisionError): division by zero
คำนวณไม่ได้ (OverflowError): int too large to convert to float
5.0
```

- การดักด้วยคลาสแม่ (`ArithmeticError`) ไม่ทำให้เสียข้อมูลชนิดจริง ตราบใดที่ยังใช้ `type(e).__name__` ตรวจสอบต่อ
- บล็อกเดียวลดจำนวน `except` ที่ต้องเขียนซ้ำเมื่อจัดการข้อผิดพลาดหลายชนิดในกลุ่มเดียวกันด้วยวิธีเดียวกัน

## Slide 60 — ตัวอย่าง: ดักด้วยคลาสกว้างเกินไป
**Key Message**: `except Exception` ปฏิบัติต่อ error จากข้อมูลผิดกับ bug ในโค้ดเหมือนกันทางกลไก

```python
def register(form):
    try:
        age = int(form["age"])
        naem = form["name"]  # พิมพ์ผิด ตั้งใจให้เกิด NameError เมื่อใช้ตัวแปรนี้ผิดชื่อ
        print(f"ลงทะเบียน {name} อายุ {age} สำเร็จ")
    except Exception as e:
        print(f"ลงทะเบียนไม่สำเร็จ ({type(e).__name__}): {e}")

register({"age": "abc", "name": "มานะ"})
register({"age": "20", "name": "ปิติ"})
```

**Output:**
```

```

- ข้อความผลลัพธ์ทั้งสองบรรทัดมีรูปแบบเดียวกันทุกประการ ทั้งที่สาเหตุต่างกันโดยสิ้นเชิง — บรรทัดแรกเป็นปัญหาจากข้อมูลนำเข้า บรรทัดที่สองเป็นข้อบกพร่องในโค้ดเอง (พิมพ์ชื่อตัวแปรผิด)
- ทั้งสองเป็นคลาสลูกของ `Exception` ทั้งคู่ `except Exception` จึงจับได้ทั้งคู่ด้วยข้อความรูปแบบเดียวกัน ต้องอาศัย `type(e).__name__` เพื่อแยกแยะสองกรณีนี้

## Slide 61 — สรุป: คลาสกลางที่พบบ่อย
**Key Message**: รู้จักคลาสกลางไว้ ช่วยออกแบบว่าจะดักที่ระดับ "กว้าง" หรือ "แคบ" แค่ไหน

| คลาสกลาง | คลาสลูกที่พบบ่อย |
|---|---|
| `ArithmeticError` | `ZeroDivisionError`, `OverflowError`, `FloatingPointError` |
| `LookupError` | `IndexError`, `KeyError` |
| `Exception` | เกือบทุกข้อผิดพลาดจากการทำงานผิดพลาดของโปรแกรม |
| `BaseException` | รากของทั้งหมด รวมถึง `SystemExit`/`KeyboardInterrupt` |

- ดักด้วยคลาสแม่ที่แคบพอ (เช่น `ArithmeticError`) รวมกลุ่มที่เกี่ยวข้องกันไว้โดยไม่ปนกับข้อผิดพลาดคนละลักษณะ
- ดักด้วย `Exception` กว้างเกินไปทำให้ error จากข้อมูลผิดกับ bug ในโค้ดถูกปฏิบัติเหมือนกันทางกลไก ต้องแยกด้วย `type(e).__name__` เอง

## Slide 62 — assert / AssertionError
**Key Message**: `assert` ยืนยันสมมติฐานภายในโปรแกรม ต่างจุดประสงค์กับ `raise`

- assertion คือกลไกระบุ "สิ่งที่ควรเป็นจริงเสมอ" ไว้ในโค้ดโดยตรง หากเท็จแสดงว่ามีบางอย่างผิดจากสมมติฐานที่ตั้งไว้
- `raise` ตรวจสอบข้อมูลจากภายนอกที่คาดเดาไม่ได้ ส่วน `assert` ตรวจสอบสมมติฐานภายในระหว่างพัฒนา/ทดสอบ
- รูปแบบ: `assert เงื่อนไข, ข้อความ` — เท็จแล้ว Python โยน `AssertionError` พร้อมข้อความอัตโนมัติ
- `AssertionError` ดักได้ด้วย `except` ตามปกติเหมือนข้อผิดพลาดชนิดอื่น

## Slide 64 — ตัวอย่าง: ป้องกันปัญหาที่ต้นเหตุ
**Key Message**: assert ชี้ตรงไปยังสาเหตุต้นทาง ไม่ใช่อาการปลายทาง

```python
def average(scores):
    assert len(scores) > 0, "รายการคะแนนต้องไม่ว่างเปล่า"
    return sum(scores) / len(scores)

print(average([80, 90, 70]))
print(average([]))
```

**Output:**
```
80.0
Traceback (most recent call last):
  File "t12_ex2.py", line 6, in <module>
    print(average([]))
          ^^^^^^^^^^^
  File "t12_ex2.py", line 2, in average
    assert len(scores) > 0, "รายการคะแนนต้องไม่ว่างเปล่า"
```

## Slide 66 — สรุป: assert vs raise vs try/except
**Key Message**: สามกลไกจุดประสงค์ต่างกัน แต่ทำงานร่วมกันในโปรแกรมเดียวได้

| กลไก | ใช้ตรวจสอบอะไร | เมื่อเท็จ/ผิดพลาด |
|---|---|---|
| `assert` | สมมติฐานภายในระหว่างพัฒนา/ทดสอบ | โยน `AssertionError` อัตโนมัติ |
| `raise` | เงื่อนไขทางธุรกิจ/ข้อมูลจากภายนอก | โยนชนิดที่ผู้เขียนโปรแกรมระบุเอง |
| `try`/`except` | ดักข้อผิดพลาดที่อาจเกิดขึ้นแล้ว | รับมือโดยไม่ให้โปรแกรมหยุดทั้งระบบ |

- `AssertionError` ดักได้ด้วย `except` ตามปกติ เชื่อมโยงทั้งสามกลไกเข้าด้วยกันได้ในฟังก์ชันเดียว

## Slide 67 — Nested try/except/finally
**Key Message**: try/except ซ้อนกันได้หลายชั้น ข้อผิดพลาดไหลจากชั้นในสู่ชั้นนอกเมื่อชนิดไม่ตรง

- โครงสร้าง try/except หนึ่งชุดวางซ้อนอยู่ภายในโครงสร้างเดียวกันอีกชุดได้ ไม่ว่าจะในส่วน try, except หรือ finally ของชุดภายนอก
- หาก except ของ try ชั้นในไม่ตรงกับข้อผิดพลาดที่เกิดขึ้น จะไหลออกไปยัง try ชั้นนอกต่อไป
- finally ของทุกชุดที่ข้อผิดพลาดไหลผ่านจะรันเสมอ ไม่ว่าจะจัดการที่ชั้นใด
- `return` ใน `finally` แย่งควบคุม — ยกเลิกข้อผิดพลาดที่กำลังไหลออกจาก try โดยสิ้นเชิง

## Slide 69 — ตัวอย่าง: ไหลจาก try ชั้นในสู่ except ชั้นนอก
**Key Message**: ข้อผิดพลาดชนิดเดียวกันถูกดักที่ชั้นต่างกัน ขึ้นอยู่กับว่าชนิดตรงกับชั้นใดก่อน

```python
records = {"1": "10", "2": "abc", "3": "30"}

def parse_record(key):
    try:
        try:
            text = records[key]
            number = int(text)
        except KeyError:
            print(f"ไม่พบรหัส {key}")
            return None
    except ValueError:
        print(f"รหัส {key} มีค่าที่แปลงเป็นตัวเลขไม่ได้: {text}")
        return None
    return number

print(parse_record("1"))
print(parse_record("2"))
print(parse_record("9"))
```

**Output:**
```
10
รหัส 2 มีค่าที่แปลงเป็นตัวเลขไม่ได้: abc
None
ไม่พบรหัส 9
None
```

- `"2"` โยน `ValueError` ที่ `int(text)` — `except KeyError` ของชั้นในไม่ตรงชนิด จึงไหลออกไปดักที่ `except ValueError` ของชั้นนอก
- `"9"` โยน `KeyError` ที่ `records[key]` — ตรงกับ `except` ของชั้นในพอดี ดักได้ทันทีโดยไม่ไหลออกไปถึงชั้นนอกเลย

## Slide 70 — ตัวอย่าง: finally หลายชั้นรันเสมอ
**Key Message**: `finally` ของทุกชั้นรันเสมอ แม้ออกจากฟังก์ชันด้วย `return` ในบล็อก except ชั้นใน

```python
stock = {"เสื้อ": 2, "กางเกง": 0}

def process_order(item, payment_ok):
    try:
        try:
            if not payment_ok:
                raise ValueError("การชำระเงินไม่สำเร็จ")
            remaining = stock[item]
        except KeyError:
            print(f"ไม่พบสินค้า '{item}' ในคลัง")
            return
        finally:
            print(f"บันทึก log การตรวจสอบสินค้า '{item}'")

        if remaining <= 0:
            raise LookupError(f"สินค้า '{item}' หมดสต็อก")
        stock[item] -= 1
        print(f"สั่งซื้อ '{item}' สำเร็จ คงเหลือ {stock[item]}")
    except ValueError as e:
        print("ยกเลิกคำสั่งซื้อ:", e)
    except LookupError as e:
        print("ยกเลิกคำสั่งซื้อ:", e)
    finally:
        print(f"ปิดการทำรายการของ '{item}'")

process_order("เสื้อ", True)
process_order("กางเกง", True)
process_order("หมวก", True)
process_order("เสื้อ", False)
```

**Output:**
```
บันทึก log การตรวจสอบสินค้า 'เสื้อ'
สั่งซื้อ 'เสื้อ' สำเร็จ คงเหลือ 1
ปิดการทำรายการของ 'เสื้อ'
บันทึก log การตรวจสอบสินค้า 'กางเกง'
ยกเลิกคำสั่งซื้อ: สินค้า 'กางเกง' หมดสต็อก
ปิดการทำรายการของ 'กางเกง'
ไม่พบสินค้า 'หมวก' ในคลัง
บันทึก log การตรวจสอบสินค้า 'หมวก'
ปิดการทำรายการของ 'หมวก'
บันทึก log การตรวจสอบสินค้า 'เสื้อ'
ยกเลิกคำสั่งซื้อ: การชำระเงินไม่สำเร็จ
ปิดการทำรายการของ 'เสื้อ'
```

- กรณี `"หมวก"` ออกจากฟังก์ชันด้วย `return` ที่อยู่ภายใน except ชั้นใน แต่ผลลัพธ์ยังแสดง `"ปิดการทำรายการของ 'หมวก'"` (finally ของชั้นนอก) ตามมาด้วยเสมอ
- `return` ต้องไหลออกจากทุกชั้นของ try/finally ที่ครอบตัวมันอยู่ตามลำดับ ก่อนจะออกจากฟังก์ชันจริง ไม่ว่า `return` นั้นจะเกี่ยวข้องกับ except ชั้นนอกหรือไม่

## Slide 71 — ตัวอย่าง: return ใน finally ยกเลิกข้อผิดพลาด
**Key Message**: `return` ใน `finally` ยกเลิกข้อผิดพลาดที่กำลังไหลออกจาก try ชั้นในโดยสิ้นเชิง

```python
def read_sensor(value):
    try:
        try:
            if value < 0:
                raise ValueError("ค่าที่อ่านได้ติดลบ ผิดปกติ")
            return 100 / value
        finally:
            print("กำลังปิดการเชื่อมต่อเซนเซอร์")
            return -1
    except ValueError as e:
        print("จับข้อผิดพลาดที่ except ชั้นนอก:", e)
        return None

print(read_sensor(20))
print(read_sensor(-5))
print(read_sensor(0))
```

**Output:**
```
กำลังปิดการเชื่อมต่อเซนเซอร์
-1
กำลังปิดการเชื่อมต่อเซนเซอร์
-1
กำลังปิดการเชื่อมต่อเซนเซอร์
-1
```

- ทั้งสามการเรียกคืนค่า `-1` เหมือนกันหมด ทั้งที่ตรรกะของ try ชั้นในควรให้ผลต่างกัน (5.0 / ข้อผิดพลาดที่ถูกดัก / ข้อผิดพลาดที่ถูกดัก)
- `except ValueError` ที่ชั้นนอกไม่มีโอกาสทำงานเลยในกรณี `-5` และ `0` เพราะ `finally` แย่งควบคุมการไหลออกจากฟังก์ชันไปก่อนที่ข้อผิดพลาดจะไปถึงบล็อกดักของชั้นนอก

## Slide 72 — สรุป: return ใน finally คือจุดที่ยกเลิกข้อผิดพลาดไหลออก
**Key Message**: `return` ใน `finally` ไม่เพียงแทนที่ค่า return แต่ยกเลิกข้อผิดพลาดที่กำลังไหลออกจาก try โดยสิ้นเชิง

| จุดที่มี `return` | ผลต่อค่าที่คืน | ผลต่อข้อผิดพลาดที่กำลังไหล |
|---|---|---|
| ใน `try` เท่านั้น | คืนค่านั้นตามปกติ (หลัง `finally` ทำงานเสร็จ) | ไม่มีผล เพราะไม่มีข้อผิดพลาดเกิดขึ้น |
| ใน `except` ชั้นใน | คืนค่านั้น หลังจาก `finally` ทุกชั้นรันครบ | ข้อผิดพลาดถูกจัดการที่ชั้นในแล้ว จึงไม่ไหลต่อ |
| ใน `finally` | แทนที่ค่า return เดิมทั้งหมด | ยกเลิกข้อผิดพลาดที่กำลังไหลออกจาก try โดยสิ้นเชิง แม้ยังไม่มี except ใดดักได้เลยก็ตาม |

- ผลที่ตามมา: `except` ของชั้นนอกที่ควรจะดักข้อผิดพลาดนั้นไม่มีโอกาสทำงานเลย เพราะข้อผิดพลาดถูกยกเลิกไปก่อนจะไปถึง

---

## Slide 73 — Bare except (การดักข้อผิดพลาดแบบไม่ระบุชนิด)
**Key Message**: `except:` ดักได้ทุกชนิด กว้างกว่าแม้แต่ `except Exception`

- บล็อกดักข้อผิดพลาดเขียนได้โดยไม่ระบุชนิดเลย เรียกว่า bare except หรือ catch-all handler ดักได้ทุกชนิดโดยไม่คัดกรอง
- ใน Python: `except:` ดักได้ถึงระดับ `BaseException` ซึ่งกว้างกว่า `except Exception` (รวมถึง `SystemExit`/`KeyboardInterrupt` ด้วย)
- ไม่แยกแยะว่าข้อผิดพลาดที่เกิดขึ้นจริงคือชนิดที่คาดการณ์ไว้ หรือเป็นข้อบกพร่องอื่นในโค้ดที่ไม่เกี่ยวข้องเลย
- ชนิดที่แท้จริงจะไม่ปรากฏในผลลัพธ์ หากโค้ดไม่ได้พิมพ์ `type(e).__name__` โดยเฉพาะ (bare except ไม่ผูกตัวแปร e ด้วยซ้ำ)

## Slide 74 — ตัวอย่าง: except เดียวจับได้หลายชนิด
**Key Message**: `IndexError` และ `TypeError` ถูกดักด้วยข้อความเดียวกันทุกประการ

```python
cart = ["เสื้อ", "กางเกง"]

def show_item(index):
    try:
        print(f"สินค้าลำดับที่ {index}: {cart[index]}")
    except:
        print("เกิดข้อผิดพลาด")

show_item(0)
show_item(5)
show_item("1")
```

**Output:**
```
สินค้าลำดับที่ 0: เสื้อ
เกิดข้อผิดพลาด
เกิดข้อผิดพลาด
```

- `show_item(5)` โยน `IndexError` (index เกินขอบเขตของ list) ส่วน `show_item("1")` โยน `TypeError` (ใช้ string เป็น index) — สองชนิดต่างกันโดยสิ้นเชิงแต่ `except:` ดักได้ทั้งคู่ด้วยข้อความเดียวกันทุกตัวอักษร
- หากไม่เปิดโค้ดต้นทางมาดู จะไม่ทราบได้เลยว่าเกิดอะไรขึ้นจริงจากข้อความที่แสดงเพียงอย่างเดียว

## Slide 75 — ตัวอย่าง: ประมวลผลชุดข้อมูลโดยไม่ให้รายการที่มีปัญหาหยุดทั้งชุด
**Key Message**: `except:` ทำให้รายการที่แปลงไม่ได้ถูกนับแยกไว้ แทนที่จะหยุดการประมวลผลทั้งชุด

```python
records = ["25", "thirty", "40", ""]

def process_batch(records):
    total = 0
    error_count = 0
    for text in records:
        try:
            total += int(text)
        except:
            error_count += 1
    return total, error_count

total, error_count = process_batch(records)
print("ผลรวม:", total)
print("จำนวนรายการที่มีปัญหา:", error_count)
```

**Output:**
```
ผลรวม: 65
จำนวนรายการที่มีปัญหา: 2
```

- `"thirty"` และ `""` ทั้งคู่โยน `ValueError` ที่ `int(text)` ถูกนับรวมเป็น `error_count` โดยไม่ทำให้การวนซ้ำรายการที่เหลือหยุดลง
- ผลลัพธ์บอกเพียงจำนวนรายการที่มีปัญหา (2 รายการ) ไม่บอกว่าแต่ละรายการล้มเหลวด้วยสาเหตุเดียวกันหรือต่างกัน — ในที่นี้ทั้งสองบังเอิญเป็น `ValueError` เหมือนกัน แต่โครงสร้างโค้ดไม่ได้ยืนยันสิ่งนี้

## Slide 76 — ตัวอย่าง: except ซ่อนบั๊กจากโค้ดเอง
**Key Message**: `except:` ปนข้อผิดพลาดจากข้อมูลจริงเข้ากับข้อบกพร่องในโค้ดโดยไม่แยกแยะ

```python
def log_reading(sensor_value):
    try:
        celsius = float(sensor_value)
        avarage = celsius / 2  # พิมพ์ผิดตั้งใจ (ประกาศตัวแปรผิดชื่อ)
        print(f"ค่าเฉลี่ยที่คำนวณได้: {average}")
    except:
        print(f"อ่านค่าจากเซนเซอร์ไม่สำเร็จ: {sensor_value}")

log_reading("abc")
log_reading("40")
```

**Output:**
```
อ่านค่าจากเซนเซอร์ไม่สำเร็จ: abc
อ่านค่าจากเซนเซอร์ไม่สำเร็จ: 40
```

- `log_reading("abc")` โยน `ValueError` จริงจากการแปลงชนิดข้อมูล — ข้อความที่แสดงตรงประเด็น
- `log_reading("40")` แปลงค่าเป็น `float` สำเร็จ แต่บรรทัดถัดมาอ้างถึงตัวแปรชื่อ `average` ที่ไม่เคยถูกกำหนดค่า (พิมพ์เป็น `avarage`) จึงโยน `NameError` แทน — `except:` แสดงข้อความเดียวกันกับกรณีแรกทุกประการ ทั้งที่ค่า `"40"` ที่ป้อนเข้ามาถูกต้องสมบูรณ์และสาเหตุจริงคือข้อบกพร่องในโค้ดเอง ซึ่งเกิดซ้ำทุกครั้งไม่ว่าจะป้อนค่าใด

## Slide 77 — สรุป: bare except vs except ที่ระบุชนิด
**Key Message**: การระบุชนิดหรือพิมพ์ `type(e).__name__` คือสิ่งที่ทำให้ทราบสาเหตุที่แท้จริง

| รูปแบบ | ดักได้กว้างแค่ไหน | ชนิดที่แท้จริงปรากฏหรือไม่ |
|---|---|---|
| `except:` | ทุกชนิดถึงระดับ `BaseException` | ไม่ปรากฏ เว้นแต่พิมพ์ `type(e).__name__` เอง |
| `except Exception as e` | เกือบทุกชนิดจากการทำงานผิดพลาดของโปรแกรม | ปรากฏได้ผ่าน `type(e).__name__` หรือ `e` |
| `except ValueError as e` | เฉพาะชนิดที่ระบุ (และคลาสลูก) | ปรากฏชัดเจนตั้งแต่ชื่อบล็อก |

- ทั้งสามตัวอย่างในหัวข้อนี้แสดงผลลัพธ์เหมือนกันทุกประการทั้งที่สาเหตุต่างกัน — ต้องแก้ไขโค้ดชั่วคราวให้พิมพ์ `type(e).__name__` หรือใช้ `except Exception as e` แล้วพิมพ์ `e` จึงจะเห็นความแตกต่างระหว่างกรณีต่าง ๆ ได้

---

## Slide 78 — Re-raise และ Exception Chaining
**Key Message**: โยนข้อผิดพลาดซ้ำ หรือแปลงเป็นข้อผิดพลาดใหม่โดยยังรักษาสาเหตุเดิมไว้ได้

- re-raise: except ทำงานบางอย่าง (เช่นบันทึก log) แล้วให้ข้อผิดพลาดยังไหลต่อไปยังผู้เรียกเหมือนไม่ได้ถูกดักไว้เลย
- exception chaining: แปลงข้อผิดพลาดระดับล่างให้เป็นข้อผิดพลาดเฉพาะโดเมนมากขึ้น โดยรักษาข้อมูลต้นทางไว้
- `raise` เปล่าในบล็อก except: โยนข้อผิดพลาดตัวเดิมซ้ำออกไปทั้งหมด
- `raise ExceptionใหมX(...) from เดิม`: โยนชนิดใหม่พร้อมแนบข้อผิดพลาดเดิมไว้ใน `__cause__`
- `raise Exceptionใหม่(...) from None`: ระงับการแสดงข้อผิดพลาดเดิมใน traceback (ยังคงบันทึกไว้ใน `__context__`)

---

## Slide 79 — ตัวอย่าง: raise เปล่า (re-raise พื้นฐาน)
**Key Message**: `raise` เปล่าโยนข้อผิดพลาดตัวเดิมซ้ำ หลังแทรกการทำงานบางอย่างระหว่างทาง

```python
def safe_divide_logged(a, b):
    try:
        return a / b
    except ZeroDivisionError:
        print(f"บันทึก log: พบการหารด้วยศูนย์ (a={a}, b={b})")
        raise

try:
    safe_divide_logged(10, 0)
except ZeroDivisionError:
    print("โปรแกรมหลักจับข้อผิดพลาดได้อีกครั้งหลังถูกโยนซ้ำ")

print(safe_divide_logged(10, 2))
```

**Output:**
```
บันทึก log: พบการหารด้วยศูนย์ (a=10, b=0)
โปรแกรมหลักจับข้อผิดพลาดได้อีกครั้งหลังถูกโยนซ้ำ
5.0
```

- `raise` ที่ไม่มีสิ่งใดต่อท้ายใช้ได้เฉพาะภายในบล็อก except ที่กำลังจัดการข้อผิดพลาดอยู่เท่านั้น เพราะ Python อาศัยบริบทของข้อผิดพลาดที่กำลังถูกจัดการอยู่เป็นตัวอ้างอิง
- ข้อผิดพลาดที่ถูกโยนซ้ำยังคงเป็นอ็อบเจกต์เดิมทุกประการ (ชนิดเดิม ข้อความเดิม) ผู้เรียกฟังก์ชันยังคงต้องดักข้อผิดพลาดเองอยู่ดี ต่างกันเพียงมี log แทรกอยู่ระหว่างทาง

## Slide 80 — ตัวอย่าง: raise ... from e (Exception Chaining)
**Key Message**: `from e` แปลงข้อผิดพลาดระดับล่างเป็นข้อผิดพลาดเฉพาะโดเมน โดยไม่ทำให้ข้อมูลเดิมหายไป

```python
class ConfigError(Exception):
    pass

def load_timeout(config):
    try:
        return int(config["timeout"])
    except ValueError as e:
        raise ConfigError(f"ค่า timeout ในไฟล์ตั้งค่าไม่ถูกต้อง: {config['timeout']!r}") from e

try:
    load_timeout({"timeout": "สิบวินาที"})
except ConfigError as e:
    print("โหลดค่าตั้งค่าไม่สำเร็จ:", e)
    print("สาเหตุเดิม (__cause__):", repr(e.__cause__))
```

**Output:**
```
โหลดค่าตั้งค่าไม่สำเร็จ: ค่า timeout ในไฟล์ตั้งค่าไม่ถูกต้อง: 'สิบวินาที'
สาเหตุเดิม (__cause__): ValueError("invalid literal for int() with base 10: 'สิบวินาที'")
```

- ผู้เรียกดักเพียง `ConfigError` โดยไม่จำเป็นต้องรู้ว่าภายในฟังก์ชันใช้ `int()` แปลงค่าอยู่ แต่ยังเข้าถึงสาเหตุดั้งเดิมได้ผ่าน `e.__cause__`
- `from e` ไม่ทำให้ข้อมูลของ `ValueError` เดิมหายไปเลย เพียง "ซ่อน" ไว้เบื้องหลังข้อผิดพลาดใหม่ที่มีความหมายตรงกับโดเมนมากกว่า

## Slide 81 — ตัวอย่าง: raise ... from None
**Key Message**: `from None` ระงับการแสดงข้อผิดพลาดเดิมใน traceback โดยเจตนา

```python
class SignupError(Exception):
    pass

def validate_username(username):
    try:
        if len(username) < 3:
            raise ValueError("ชื่อผู้ใช้สั้นเกินไป")
    except ValueError as e:
        raise SignupError("ไม่สามารถลงทะเบียนได้") from None

validate_username("ab")
```

**Output:**
```
Traceback (most recent call last):
  File "t15_ex3.py", line 11, in <module>
    validate_username("ab")
  File "t15_ex3.py", line 9, in validate_username
    raise SignupError("ไม่สามารถลงทะเบียนได้") from None
SignupError: ไม่สามารถลงทะเบียนได้
```

- traceback แสดงเฉพาะ `SignupError` เพียงชนิดเดียว ไม่มี `ValueError` เดิมปรากฏเลย เพราะ `from None` กำหนด `__cause__` เป็น `None` อย่างชัดเจน
- หากเปลี่ยนเป็น `raise SignupError(...)` เฉย ๆ (ไม่มี `from` ต่อท้ายเลย) traceback จะแสดงทั้งสอง error ต่อเนื่องกัน คั่นด้วย `"During handling of the above exception, another exception occurred:"` เพราะ Python บันทึก `__context__` อัตโนมัติทุกครั้งที่โยนใหม่ระหว่างอยู่ใน except ไม่ว่าจะมี `from` หรือไม่ก็ตาม

## Slide 83 — สรุป: สามรูปแบบของการโยนข้อผิดพลาดใหม่ในบล็อก except
**Key Message**: เลือกรูปแบบตามว่าต้องการให้ traceback แสดงข้อผิดพลาดเดิมมากน้อยแค่ไหน

| รูปแบบ | `__cause__` | ปรากฏใน traceback หรือไม่ |
|---|---|---|
| `raise` (เปล่า) | — (ไม่ใช่การสร้างข้อผิดพลาดใหม่ โยนตัวเดิมซ้ำ) | ตัวเดิมเท่านั้น |
| `raise NewErr(...) from e` | ตั้งค่าเป็น `e` | ทั้ง `NewErr` และข้อผิดพลาดเดิม |
| `raise NewErr(...)` (ไม่มี from) | เป็น `None` แต่ `__context__` บันทึกอัตโนมัติ | ทั้งสอง คั่นด้วย "During handling..." |
| `raise NewErr(...) from None` | เป็น `None` โดยเจตนา | เฉพาะ `NewErr` เท่านั้น |

- ทั้งสี่รูปแบบใช้กลไกเดียวกันของ Python ต่างกันเพียงว่าจะให้ traceback แสดงข้อผิดพลาดต้นทางมากน้อยเพียงใด ข้อมูลต้นทางยังคงเข้าถึงได้ผ่าน `__cause__`/`__context__` เสมอไม่ว่าจะเลือกรูปแบบใด
